# 普通消息发送与失败状态修复

## 背景 / 原因

聊天接口同时支持普通发送、运行中排队和直接引导。接口请求模型包含直接引导的可选字段；普通首次发送时，即使这些字段为空，也可能因参数传递不兼容而返回服务器错误。前端保留了失败的发送记录，却没有显示失败状态，用户容易将其误认为已经送达的消息。

## 具体设计

- 会话空闲时，普通发送应启动一轮聊天；接口模型的可选控制字段为空或省略均应正常处理。
- 运行中的排队及直接引导继续使用原有消息交付链路；直接引导的任务校验和重试识别字段只在该链路中处理。
- 普通消息提交期间显示“发送中”；提交失败且没有收到任务编号时，保留消息内容并显示“发送失败”。
- 成功送达后，以后端聊天历史为准，移除对应的本地待发送记录。
- 用户可以连续发送相同文字，不能仅因内容相同就合并两次独立发送。

## 实现指引

- 后端修改范围为 Gateway 接口进入消息与会话编排层的参数转换：`agent-alpha/agent/server/agent_manager.py` 中的 `submit_chat`。
- 前端修改范围为入口展示层：`agent-alpha/frontend/src/App.tsx` 中普通发送的本地消息状态。
- 不改模型调用、会话存储格式和多 Agent 执行规则。

## 验收标准

- 新会话通过普通聊天请求发送第一条消息时，不因空的引导字段返回 HTTP 500，且只启动一个任务、保存一次用户消息。
- 内部调用省略控制字段时，同样正常启动聊天。
- 运行中排队、直接引导及已结束任务的引导重试仍遵循原有规则。
- 普通发送失败后，消息具有明确失败标记；连续发送相同内容仍保留各次发送的独立记录。
