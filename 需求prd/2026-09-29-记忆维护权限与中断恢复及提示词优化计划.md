# 2026-09-29 记忆维护权限、中断恢复与提示词优化计划

本文记录本轮背景、具体设计、执行顺序和验收标准，不记录实施情况。代码实施须在计划讨论收束后开始。

## 1. 背景与目标

当前 user.md 混入对齐功能生成的固定指令、求职表单填写口径和其他临时任务要求，长期用户画像提取不足。用户添加排除对齐内容的补充要求后，最近两次手动任务仍未修改文档；任务记录显示两次仅允许更新技能 references。

用户本轮明确：记忆是否用于日常对话，与记忆文档能否维护应分开；自动整理遇到中断、临时故障和意外情况，应能恢复，不应永久停止或悄悄丢失任务。

目标：先修复文档维护与执行恢复链路，再改善整理和审核提示词。复用现有整理 Agent、审核 Agent、受限工具和持久化任务，不另建记忆系统。

## 2. 已核查的问题与边界

- 审核工具 memory_edit 已注册，能实际修改两份文档。缺失工具不是当前问题。
- 前端手动目标、后端 allowed、文档及历史读取、实际写入均与 enabled 耦合。
- 旧草稿第 9.1 节明确采用该耦合；本轮以用户最新要求替代这部分开关语义，不能将旧实现描述为偏离旧设计。
- 没有成功操作统一显示 no_change，不能区分审核跳过、权限拒绝或确实没有候选。
- 任务完成后删除提案和审核过程，缺少持久化的简短处理原因。
- 页面轮询任务状态，但任务完成后不重新读取文档和历史版本。
- 失败任务最多自动尝试三次；失败的自动任务又阻止后续自动启动，可能长期停住。
- 原始日志保护只覆盖 organizing/reviewing，等待重试的失败任务未受保护。
- 文件写入与操作完成记录分开持久化，存在文件已写、回执或记账未完成的中断窗口。
- 仅依据审核模型正常返回便结束审核，缺少逐项处理完整性校验。

最近任务的逐项审核原因已被清理，不能还原它们是否调用过被拒绝的文档修改工具。本轮使用可控故障和工具链测试验证修复，不根据缺失记录推断模型行为。

## 3. 后端与入口设计

### 3.1 分离记忆使用与维护

| 动作 | 控制条件 |
| --- | --- |
| 日常实例加载 user.md、memory.md | enabled |
| 自动维护两份文档 | documents_auto_update |
| 自动维护技能 references | skills_auto_update |
| 手动整理 | 本次选择 documents / references，不受上述三个开关限制 |
| 管理页查看、直接编辑、恢复历史 | 保留现有容量、版本和编辑互斥校验 |
| 整理/审核读取已有文档与历史 | 不受 enabled 限制，保持受限读取范围 |

写入仍校验任务有效性、本批目标、文件范围和容量。自动任务运行期间关闭对应自动更新开关，拒绝后续对该对象写入并记录原因；关闭 enabled 不影响维护任务。开启原先未选择的对象，不扩大当前批次。

前端解除 enabled 对手动文档目标和开始按钮的限制，更新开关说明，并显示后端返回的本次更新对象。

### 3.2 明确审核结果

每条提案必须有明确结果：已执行、审核跳过及原因、目标写入被拒绝及原因，或尚未完成。为审核角色提供受限的跳过/完成确认能力；不能仅凭模型正常结束判定所有提案已处理。

对存在未处理提案的任务，继续恢复审核或进入明确的可恢复错误，不报告无需修改。审核范围仍限于整理提案。

保存小型结果摘要：对象、处理状态、简短原因、提案数和实际修改数。页面区分无候选、全部审核跳过、目标被禁用、部分完成和异常待恢复。无需长期保存完整模型对话；历史版本继续保留最近八版。

实际修改数以文件内容发生变化为准，同内容替换不算新增修改。整理结束后重新读取当前文档和历史版本，避免页面显示旧正文。

### 3.3 中断与重试

| 情况 | 预期处理 |
| --- | --- |
| 正常关闭应用、进程被结束、断电 | 保存过的批次和阶段在启动后恢复；不重新选取范围或替换补充提示词 |
| 整理未提交提案 | 优先从有效检查点和临时笔记继续；检查点不可用则重做同一批整理 |
| 提案已提交 | 直接进入审核，不重复整理 |
| 审核部分完成 | 跳过已确认完成项，继续未处理项 |
| 网络、模型服务、暂时文件占用故障 | 使用有上限的退避间隔自动重试，不因累计三次失败永久停掉整理 |
| 持续的配置错误、容量或参数问题 | 显示可操作原因，修正后可重试；不高频循环，不误报完成 |
| 用户主动编辑导致取消 | 永久取消该批次，拒绝迟到写入，重启不复活 |
| 自动更新开关变化 | 按写入时对应开关处理，记录跳过；不回滚已保存内容 |
| 没有日志或证据不完整 | 不编造来源；明确记录空范围或证据缺口，不能当作完整审查成功 |

自动重试采用逐步延长且封顶的间隔；正常运行后重置连续故障计数。持久化下次重试时间、失败阶段和原因。一个待恢复任务继续占用单任务名额，不并行启动第二批，也不静默用新任务覆盖失败批次。

持续无法自行恢复时保留批次并在页面显示原因，提供重试或明确放弃的操作。主动放弃与技术中断分开记录，放弃不把未处理轮次标为已完成。

补齐运行停滞检测：对没有检查点或工具进展的异常长时间停滞进行受控中断，交由恢复流程处理；阈值依据现有模型请求超时确定，不误杀正常长日志读取。任务取消、关闭和超时共用现有进程停止机制。

### 3.4 防止重复写入与覆盖

执行前持久化稳定操作标识、目标、预期修改前版本和待写内容；执行后持久化结果，再确认工具成功。

重启遇到未确认操作时检查文件：若已与待写内容一致，补记成功；若仍为预期旧版本，继续执行；若出现第三种内容，报告冲突，不能盲目覆盖。恢复操作不依赖模型重新生成相同 operation_id。

同一批次对同一文档的操作保持顺序，恢复不得用较早操作覆盖后续成功内容。保持原子文件替换和批次历史版本去重；不要求跨所有文件整批回滚。

### 3.5 进度、证据和清理

- 只有全部提案有终结结果且批次最终结果持久化后，才推进自动进度。
- 技术失败、未完成和取消不推进；已有部分成功写入保持可追踪。
- 对应对象被自动开关拒绝属于明确的本批跳过，延续原有共用进度规则，不建立按对象补做队列。
- 本批日志清单和补充提示词在恢复期间固定；用户更改补充要求仅影响下一批。
- 保护所有待恢复任务依赖的原始日志，不只保护正在执行的状态；最终完成或明确放弃后释放保护。
- 已被用户删除或原本缺失的日志不可能还原，需记录证据缺口，禁止根据缺失内容制造记忆。
- 临时笔记、检查点和未确认操作在可恢复阶段保留；终结结果持久化后清理。清理失败只重试清理，不重新运行模型任务。

## 4. 提示词设计

### 4.1 整理 Agent 固定提示词

- 先读取现有文档，再读取本批原始日志；同时检查新增、纠错、删除、合并，不只追加。
- user.md 优先保留有明确依据的长期身份背景、教育与职业经历、长期目标，以及跨任务适用的沟通和表达偏好；无需每项齐全，不为填满容量而编造。
- 不从行为推断性格、身份或未表达的偏好。简历内容须在可读取日志中有直接来源且明确属于用户本人，不能把改写示例或投递表单口径当成事实。
- 排除对齐按钮的固定文字及同类功能生成指令；不能仅凭重复出现判断为个人偏好。
- 排除某次投递填写年限、岗位操作步骤、一次性页面样式、临时格式和任务进度。若用户另外明确提出跨任务长期偏好，可按其真实范围记录。
- 当前记忆不是可靠事实来源；按来源与新要求检查已有错误条目，提出清理提案。
- 补充要求属于本批整理指令，不能机械转成长期记忆。用户明确要求排除某类内容时，可据此提出清理现有内容的提案。
- 分清 user.md、memory.md 与技能 references 的归属，不把临时任务内容换个文件继续长期保存。
- 保留逐段读取、继续位置、临时笔记、来源位置和容量要求。

### 4.2 审核 Agent 固定提示词

- 按原始证据逐项核对，允许修正提案所涉内容，再通过 memory_edit 实际执行。
- 检查整份待写文档的保留内容，防止错误旧条目随整篇替换继续留下；修正范围仍受提案约束，不能随意新增其他修改。
- 删除错误、重复、临时或功能生成的旧条目属于维护；用户当前明确排除要求可作为相应清理依据。
- 新增画像必须有本人且明确的事实来源；没有证据则跳过，不主动打开任意文件、猜测身份或重建缺失简历。
- 跳过时明确记录原因；调用修改工具后检查返回结果，失败不能宣称成功，仍有未处理项不能宣称审核完成。
- 从后端提供的容量、本批目标、已完成操作和待处理提案继续执行，避免恢复时重做。

自动与手动继续使用同一套固定角色提示词；页面两个补充提示词分别保存、分别快照，并同时交给整理和审核。保留用户已保存的补充文字，不擅自覆盖。

## 5. 涉及层与实施顺序

| 阶段 | 涉及层 | 工作与验证 |
| --- | --- | --- |
| 1 | 权限/安全、Tool、入口 | 分离加载与维护开关；验证关闭 enabled 后手动读写正常，自动仅受相应自动更新开关控制 |
| 2 | 消息与会话编排、Agent Runtime、持久化、Tool | 完善逐项结果、重试、恢复、操作记账、日志保护和停滞处理；验证故障注入后继续完成同批任务 |
| 3 | Context / Prompt | 更新整理、审核固定提示词与任务指引；验证排除临时要求、清理旧内容和画像证据标准 |
| 4 | 入口、Gateway | 展示目标和原因、重试入口、完成后刷新正文；验证 API 返回与前端状态处理 |
| 5 | 文档 | 同步旧文档中被替代的开关语义；实际实施后另写开发日志，不把实施结果写入本文 |

优先修复执行链路，再改内容判断规则；不新增 Agent，不重构整个 Harness，不改变现有日志保留期限、文档容量和日常实例加载时机。

## 6. 验收与测试

使用少量有针对性的参数化与故障注入测试，测试产物和 pytest 缓存放 temp，不运行浏览器测试。

1. 开关组合：enabled 开/关、自动更新开/关、手动文档/技能单选与双选；后端与页面目标一致。
2. 阶段恢复：整理提交前后、审核部分完成、保存最终状态前中断；不丢提案、不重复整理、不提前推进进度。
3. 写入窗口：文件写前、写后记账前、记账后回执前中断；恢复结果一致，历史版本不重复，用户新内容不被覆盖。
4. 重试与生命周期：连续超过三次临时失败后仍能恢复；重启遵守退避时间；待恢复任务不被新任务覆盖；停滞任务释放执行进程。
5. 用户竞争操作：编辑取消、取消后迟到调用、运行中切换 enabled/自动开关、同一批重复工具调用；手动内容优先，取消不复活。
6. 证据与清理：待重试日志受保护、日志真实缺失、清理失败、空范围；不编造证据、不把清理失败当作需重新执行。
7. 内容与结果：对齐固定文字、投递年限、真实长期背景、用户清理要求、无证据画像、同内容替换、审核全跳过、权限拒绝、部分成功；逐项结果可解释且计数真实。
8. 提示词质量不能只靠替身模型测试证明。另用去标识化代表样例核对整理/审核输出，并与工具链验证分开报告；不为了验收重跑全部私人历史或自动改写现有真实记忆。

最终成功标准：能独立控制使用和维护；临时故障可恢复且不永久停住；取消和冲突不会覆盖用户内容；页面能解释是否修改及原因；两份固定提示词明确筛选长期信息并维护已有错误记忆。
