# 2026-09-21 Browser Harness 共用资料与容量维护

## 背景/原因

新对话和子 Agent 原来按会话编号创建独立的浏览器资料。用户在旧资料中登录 Chrome 的 Google 账号后，新对话打开另一份空资料，表现为登录丢失；重复资料与缓存也使 `state/browser-harness` 持续增长。用户希望所有对话复用一套账号资料，并优先控制文件体积。自动清理即使导致重新登录，也不能拖慢界面启动、打断正在使用的浏览器或让 Agent 的任务循环因清理失败而中断。

## 具体设计

### Tool / Skill / Plugin 能力层

- `browser_harness_exec` 继续作为薄工具入口。Browser Harness 0.1.13 自己负责 daemon 健康检查、失效连接恢复和标签页恢复；Alpha 不修改第三方源码。
- 所有会话和 Agent 统一使用 `state/browser-harness/browser-profile`、相同的 Harness runtime 目录及固定 `BU_NAME=alpha-shared`。实施前确认旧共用资料含 Chrome 账号记录，因此没有复制或拼接 Cookie 数据库；用户随后要求一次性重置，旧登录资料已经清空。
- 本设计取代《2026-09-18-子agent与消息插队设计草稿》中“按 Agent ID 使用各自浏览器 profile 和 daemon”的旧约定。
- Alpha 仍需为专属资料目录启动 Chrome、在人工登录和 CDP 模式间切换，并通过 `BU_CDP_URL` 连接；上游默认的本地浏览器发现无法定位 Alpha 的专属目录。
- 浏览器工具调用和应用退出时的浏览器关闭使用同一个跨进程文件锁。锁随进程退出自动释放。已连接的健康 CDP 不因新 Agent 运行对象创建而强制 `--reload`，由 Browser Harness 自行检查连接。

### Workspace / Memory / State 持久化层

- 只统计当前 Browser Harness 的 `state/browser-harness` 与 `temp/browser-harness`；不包含 Chrome 安装程序、用户下载和已退役的 `state/browser` 系统。
- 超过 500 MiB 才启动维护，目标降至 300 MiB。先删除临时产物、浏览器页面和代码缓存、离线缓存及模型缓存，再回收旧的按 Agent 划分的 Browser Harness 资料。若清理成功后仍超过 500 MiB，最后重置共用资料。Cookie 与 Google 账号配置尽量留到最后；Chrome 没有提供可可靠单独抽取“仅 Google 账号文件”的接口，因此最后重置可能要求重新登录。
- Web 界面加载后才请求启动后台维护线程；线程启动不等待容量扫描。每次检查和删除有 10 秒预算；发现活跃工具调用、专属 Chrome 窗口或旧资料对应的 Chrome 进程时不清理。窗口打开期间持续刷新保护时间，关闭后再留约 5 分钟空闲缓冲。人工登录窗口一直开启时持续保护。
- 文件被占用、进程识别失败或超时属于维护失败，终止本次维护并记录提示；5 小时后或下次启动再试。维护失败允许暂时超出 500 MiB，不升级为资料重置。普通清理不提示；完整重置提示下次需要重新登录。

### 入口层

- Web/Electron 界面先可用，后台才检查容量。界面每分钟读取一次维护通知，并对同一通知只显示一次。CLI 的浏览器工具继续共用资料和跨进程锁；后台定期维护由 Web 后端承担。

## 验收与边界

- 模拟测试不启动真实浏览器，覆盖共用资料、跨进程互斥、活跃窗口跳过、缓存优先、失败延后及最后重置。
- 浏览器使用优先。清理若失败或未得到安全空闲机会，500 MiB 是触发线，不是任何时刻都成立的硬上限。
- 多 Agent 的浏览器工具调用依次进入共用通道；不增加整个 Agent 任务的排队规则。
- 本次不自动操作或删除用户日常 Chrome 资料，也不清理旧系统 `state/browser`。
- 用户另行明确要求的一次性重置已清空当前 Browser Harness 与旧系统的现有运行资料；这不改变上面的定期维护范围。
