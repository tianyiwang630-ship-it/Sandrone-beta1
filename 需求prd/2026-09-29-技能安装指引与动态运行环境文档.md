# 2026-09-29：技能安装指引与动态运行环境文档

> 文档性质：待实施的需求与具体设计。本阶段仅编写 PRD，不修改功能代码，不安装技能，不执行真实安装演练。
> 本文的代码现状以编写时读取的源码为依据；“拟新增”“应当”“实施步骤”均为后续设计，不代表已完成。

## 1. 背景 / 原因

Alpha 通过自己的后端、终端工具和技能加载器运行技能。其技能目录、Python、命令入口、环境变量以及资料目录，与第三方 README 中常见的 Codex、Claude Code 布局不同。直接照搬上游命令，容易安装到错误位置，或者安装成功但后续使用了错误的 Python。

现有 `agent-alpha/skills/install-alpha-skill/SKILL.md` 已承担路径适配职责，但部分内容落后于实现：

| 现有说明 | 当前源码行为 | 本次处理 |
| --- | --- | --- |
| Bash 默认在 Alpha 根目录执行 | 默认使用当前 Agent 的 workspace | 安装说明改为读取实际路径，并显式指定 `working_dir` |
| Python 工具必须装进固定 `.venv` | 开发版默认 `.venv`；打包版使用随包解释器；Browser Harness 已有独立环境 | 指向运行时解析的共用 Python，保留冲突时隔离的安装原则 |
| npm 全局安装使用宿主目录 | `NPM_CONFIG_PREFIX`、`NPM_CONFIG_CACHE`、`NODE_PATH` 已指向 Alpha 数据根内部 | 修正技能及系统提示词中矛盾的说明 |
| 内置资源、可写数据都按 `agent-alpha/...` 描述 | EXE 已分离程序根和数据根 | 由后端提供各目录的实际绝对路径 |
| 用户要求即可修改核心代码 | 运行时路径策略对 `agent`、`session-log` 的写入仍有禁止规则 | 文档忠实描述权限，不把用户安装请求解释为修改核心代码的授权 |
| 安装后立即加载、执行上游 smoke test | 用户希望安装结束后自行在新对话确认 | 改为简单的新对话验证提示，不增加热加载和真实安装演练 |

本次采用轻量方式：后端生成当前环境事实，系统提示词提供阅读入口，安装技能说明如何据此安装。避免在技能、提示词、手写路径表中重复维护同一组路径。

## 2. 已确定的产品要求

1. 普通技能优先复用应用现有的共用 Python 环境；先检查依赖，兼容就安装到共用环境，明确冲突才考虑独立环境。
2. 不因为每安装一个技能就创建一个 Python 环境，也不另建一套所有技能专用的共享 Python。
3. 已有安装优先复用。Browser Harness 保持现有安装和接入方式，不重新安装或迁移。
4. 技能安装覆盖技能文件、依赖和必要配置。新增后端工具、修改工具注册表或核心代码属于应用接入，不能自动作为安装步骤执行。
5. 后端提供工作指引文档，内容包括实际路径、必要的环境变量和使用规则；模型按需读取。
6. 路径由后端在构建系统提示词的链路中解析。禁止写死开发机盘符、用户名、项目目录名称或某次打包的安装路径。
7. 相对路径必须有明确基准，再由后端拼接、规范化；不得依赖 worker 的进程 cwd 恰好位于应用目录。
8. “实时解析”指根据当次 Runtime / 提示词构建使用的运行配置生成，不是每个 token、每次流式输出或每次工具调用都重写文件。
9. 安装完成后，引导用户新建对话，发送：`请检查「技能名称」是否安装成功。`
10. 保持改动范围小。不增加技能热加载、安装管理服务、依赖数据库、能力注册中心、前端页面或新接口。
11. 安装时允许修改第三方技能 MD 中适配 Alpha 所必需的路径和调用指令；其他内容保持原样。该权限不自动扩展到附带脚本或应用代码。
12. 本次功能实施范围增加“受管独立 Python 环境”的安装与调用适配：由应用开发统一修改沙箱相关校验和终端预检；以后安装技能时，模型只使用这些已经提供的能力，不自行修改沙箱。
13. 安装过程中若新建独立 Python 环境，必须主动告知用户创建原因、实际环境位置和后续调用方式；即使后续安装失败，也要说明已创建的环境及当前状态。告知不新增一次审批，也不要求用户手动激活环境。
14. 依赖冲突后允许在 Alpha 指定目录创建独立环境并通过现有 Bash 工具直接调用；不需要为每个技能增加工具注册项或后端包装工具。具体目录、命令、判断和拒绝范围见第 10.3 节。

## 5. 目标调用链

### 5.1 正常构建流程

```text
CLI 或 Web/Electron 的执行 worker
  -> AgentRuntime 初始化并沿用现有运行环境注入
  -> 创建技能加载器和工具
  -> AgentRuntime._build_system_prompt()
       -> 读取本 Runtime 使用的程序根、数据根、技能目录
       -> 复用运行时解析逻辑获得共用 Python 和环境字段
       -> 生成 runtime-info.md 的完整正文
       -> 写入 <数据根>/state/runtime-info.md
       -> 将写入成功的实际绝对路径传给 build_system_prompt()
  -> 构造 ContextManager、进入现有 Agent Loop
  -> 模型安装技能或处理路径问题时，用现有 read 工具读取文档
```

### 5.2 生命周期约定

- 在普通 Runtime 的系统提示词构建时生成；不要求一打开桌面窗口就立刻生成。
- 新 Runtime 或原有正常重建流程再次经过此处时，按当时实际配置重新生成。
- Runtime 复用期间不增加轮询，不在每轮普通消息、每次工具执行或 token 输出时重新写文档。
- 文档表示本次构建时的公开运行事实。运行中手动改变环境并不会因此获得新增的热更新能力。
- 当前 worker 会切换到 workspace；生成文档的路径仍从数据根计算，与 cwd 无关。
- 多个 Agent 使用同一 Alpha 数据根时共用文档；不同数据根生成各自的文档。
- 专用记忆角色保留自己的提示词和工具集合。具有普通文件、技能能力的主 Agent / 子 Agent 沿用上述流程。

## 6. 动态路径解析契约

### 6.1 唯一事实来源

- 根目录、解释器从当前 Runtime 使用的现有布局解析逻辑获取。
- 重定向后的变量从当前数据根对应的 `build_runtime_env()` 结果获取。
- 内置 / 第三方技能目录使用 Runtime 已交给 SkillLoader 的目录，不能另算一套与实际扫描范围不同的目录。
- 新增模块只整理、渲染、保存这些事实，不接管布局决策、PATH 注入或权限判定。
- 同一次提示词构建先确定这一组值，文档正文、文档存放路径和提示词引用均使用这组值。

### 6.2 路径表示

本文使用以下符号说明拼接关系；它们不是要求新增的 shell 环境变量：

| 符号 | 含义 | 来源 |
| --- | --- | --- |
| `A` | 程序资源根 | 当前 Runtime 使用的 `APP_ROOT` / 内置技能目录所属程序根 |
| `R` | 可写运行数据根 | 当前 Runtime 使用的 `PROJECT_ROOT` / `AGENT_ALPHA_ROOT` |
| `P` | 共用 Python 解释器 | `runtime_python(R)` 的有效解析结果 |
| `W` | 当前 Agent 的工作区 | 实例的 `workspace_root`，仅用于各自提示词 |

动态路径表达式如下：

| 用途 | 表达式 | 模型最终看到的内容 |
| --- | --- | --- |
| 环境文档 | `R / "state" / "runtime-info.md"` | 已规范化的绝对文件路径 |
| 内置技能 | Runtime 的 `skills_dir`，通常为 `A / "skills"` | 实际扫描目录 |
| 第三方技能 | Runtime 的 `agent_home_skills_dir`，通常为 `R / "home" / ".agents" / "skills"` | 实际安装目录 |
| 命令入口 | `R / "bin"` | 绝对目录 |
| 共用 Python 的 CLI 目录 | 由选定解释器 P 的布局解析，见第 6.3 节 | 实际 Scripts / bin 绝对目录，与 Python 所在目录分别展示 |
| 长期资料 | `R / "state"` | 绝对目录；能力资料按名称放子目录 |
| 临时产物 | `R / "temp"` | 绝对目录 |
| 安装暂存区 | `R / "temp" / "skill-install"` | 绝对目录，安装任务可按来源建立子目录 |
| 缓存 | `R / "cache"` | 绝对目录 |
| uv 工具环境 | 运行环境的 `UV_TOOL_DIR` | 实际绝对目录 |
| 普通技能独立 Python 环境 | `R / "tools" / "venvs"` | 动态根目录，环境按技能名放直属子目录；新建规则见第 10.3 节 |
| uv 命令入口 | 运行环境的 `UV_TOOL_BIN_DIR` | 实际绝对目录 |
| 服务变量配置 | `R / "config" / "runtime_env.local.json"` | 配置文件位置，不展示其内容 |
| MCP 资源 / 注册文件 | 现有 Runtime 提供的 MCP 路径 | 实际资源路径，不代表允许自动修改注册 |

要求：

1. 后端拼接时使用 `Path` 和已解析的根；生成给模型阅读的文件路径必须是绝对路径。
2. `state/runtime-info.md` 等相对片段只作为代码内的固定结构，不从当前终端目录解释。
3. 不将 PRD、测试数据或开发者机器上的实际绝对路径复制进生产代码。
4. 修改安装位置、盘符或用户名后，新建 Runtime 应自动得到新的文档路径和内容。
5. 对已有启动配置采用原有解释规则；本次不另行定义外部环境变量中的相对根路径语法。
6. 提示词中的 `WORKSPACE_ROOT` 是展示字段，当前不是保证存在的 shell 环境变量；模型不能默认使用 `$WORKSPACE_ROOT`。
7. 文档中的标签、变量名和真实环境变量分开描述。开发版可能未注入 `AGENT_ALPHA_PYTHON`、`AGENT_ALPHA_APP_ROOT`，但后端仍能解析其对应事实；不要因此顺带改变现有注入策略。

### 6.3 解释器与 CLI 目录必须对齐实际执行端

- 在 `runtime_layout.py` 复用 / 提取接收已解析布局与目标数据根的小型选择函数：目标根等于布局数据根时使用其配置 Python（包括开发版 `AGENT_ALPHA_PYTHON` 覆盖）；不同根采用该目标根的开发解释器，不借用另一实例的覆盖。`runtime_python()` 和 `build_runtime_env(base_env=...)` 均调用它，后者必须使用传入的 base_env 解析布局，不能重新读取另一套全局环境。
- 提示词、环境文档、Bash 默认解释器及沙箱共用解释器识别使用该结果。有效覆盖应正常支持；解释器缺失时报告路径，不悄悄回退另一 Python。文档生成不启动解释器。
- 在 `runtime_paths.py` 集中解析 Python 所在目录和 CLI 目录：现有 Windows venv 的 P 已在 Scripts 中，CLI 目录即该目录；随包 P 在 backend-python 中，CLI 目录为其下 Scripts；POSIX venv 使用已有 bin。对当前支持布局以外无法确定的形式明确诊断，不猜测宿主目录。
- `build_runtime_env()` 将 P 所在目录和解析出的 CLI 目录加入本次 PATH 前部并去重，再保留原有 Alpha bin 等项目。目录事实可在安装前公布，但不能据此宣称具体命令已存在。
- 当前 `package-windows.ps1` 会移除随包 Python 的 Scripts 目录。以后安装生成的新 CLI 可使用上述目录；仅补 PATH 不会恢复打包时删掉的入口。缺失入口要报告，不自动修改打包流程或生成包装器。
- 不为这些事实新增全局环境变量；后端在消息组装时解析、写入文档，终端按同一规则构造实际执行环境。

## 7. 后端环境文档的具体设计

### 7.1 存储与所有权

- 文件名固定为 `runtime-info.md`，位置由 `R / "state" / "runtime-info.md"` 动态产生。
- UTF-8 文本，无需额外清单、数据库或版本协议。
- 是后端生成的说明文件，不是配置源；模型不能通过修改它切换 Python、改变权限或安装位置。
- 不放到用户 workspace，不自动修改用户的 `AGENTS.md` / `SOUL.md`。
- 不提交实际运行文档到 Git。现有 `agent-alpha/.gitignore` 已忽略 `/state/`，无需为此增加新的忽略体系。
- 文档不包含会话 ID、当前任务、当前 workspace、用户消息或 Agent 私有记忆。

### 7.2 推荐代码组织

拟新增一个小模块 `agent-alpha/agent/core/runtime_info.py`，只承担：

1. 接收已经确定的运行事实，生成 Markdown 字符串。
2. 将完整字符串写入指定数据根的文档位置，并返回最终 `Path`。

建议接口形态：

```python
render_runtime_info(
    *,
    app_root,
    data_root,
    python_executable,
    skills_dir,
    third_party_skills_dir,
    runtime_env,
) -> str

write_runtime_info(*, data_root, content) -> Path
```

这些名称是实施定位建议；不要求增加类、服务容器或全局实例缓存。事实收集接在 `AgentRuntime._build_system_prompt()`，复用现有 `runtime_layout` / `runtime_paths`。`build_system_prompt()` 保持文本组装职责，接收文档路径以及已解析的默认 Python，避免再次从另一处推导解释器。

### 7.3 文档固定内容

生成文档按以下顺序组织，不扫描整个机器生成软件清单：

1. **说明**：由 Alpha 后端生成，按需阅读，不作为配置文件。
2. **当前模式和路径**：开发 / 分离安装布局、程序根、数据根、共用 Python、共用 Python 的 CLI 目录、内置与第三方技能目录、bin、state、temp、cache、uv 工具环境、普通技能独立环境根、服务配置文件。
3. **公开环境变量**：名称、实际值、用途；只来自下节定义的允许集合。
4. **工作指引**：工作区与数据根的分工、Bash working_dir 语义、绝对路径读取、依赖安装目标、npm 路径、服务配置入口和现有权限边界。
5. **技能安装规则**：读取安装技能，优先共用 Python、冲突才隔离、已安装复用，完成后新建对话检查。

程序根和解释器路径属于“定位事实”，不能根据字段存在就生成“该目录一定可写”“依赖已经安装”“uv 已可用”等结论。文档生成阶段不运行 `pip`、`uv`、浏览器或网络命令。

### 7.4 允许公开的环境字段

从实际运行环境中选择下列字段；缺失的可选项省略或标为未设置，不伪造变量存在：

| 类别 | 字段 |
| --- | --- |
| Alpha 根与解释器覆盖 | `AGENT_ALPHA_ROOT`、实际存在时的 `AGENT_ALPHA_APP_ROOT`、`AGENT_ALPHA_PYTHON`、`AGENT_ALPHA_BROWSER_PYTHON`、`AGENT_ALPHA_NODE_EXECUTABLE` |
| 用户目录映射 | `HOME`、`USERPROFILE`、`APPDATA`、`LOCALAPPDATA`、Windows 的 `HOMEDRIVE` / `HOMEPATH` |
| XDG 目录 | `XDG_CONFIG_HOME`、`XDG_CACHE_HOME`、`XDG_DATA_HOME`、`XDG_STATE_HOME` |
| 临时与 Python 安装缓存 | `TMP`、`TEMP`、`PIP_CACHE_DIR`、`UV_CACHE_DIR` |
| uv 工具 | `UV_TOOL_DIR`、`UV_TOOL_BIN_DIR` |
| Node / npm | `NODE_PATH`、`NPM_CONFIG_PREFIX`、`NPM_CONFIG_CACHE` |
| Python 运行设置 | `VIRTUAL_ENV`、`PYTHONUSERBASE`、`PYTHONPYCACHEPREFIX`、`PYTHONNOUSERSITE`、`PYTHONUTF8`、`PYTHONIOENCODING` |
| 其他已重定向的路径 | `HF_HOME`、`TRANSFORMERS_CACHE`、`PLAYWRIGHT_BROWSERS_PATH`、`DOTNET_CLI_HOME`、`CARGO_HOME`、`RUSTUP_HOME` |

- 不整体写入 `os.environ` 或 `build_runtime_env()` 返回值。
- 不输出 API Key、Token、Cookie、Authorization、代理凭据或 `runtime_env.local.json` 原文；未知自定义变量也不默认输出。
- 不输出 `AGENT_ALPHA_RUNTIME_PROFILE_KEYS` 等内部记录字段。
- 不完整转储宿主 PATH；工作指引说明默认解释器目录、Alpha bin、npm 工具目录等现有优先项即可。
- 不因写文档新增另一套环境变量注入。文档中的 `Python interpreter` 等事实可以存在，即使同名含义的覆盖环境变量未注入。
- Browser Harness 的 `BH_HOME`、`BH_TMP_DIR` 等由其专用执行器设置，不应被写成普通 Bash 一定具有的全局变量。本次不把浏览器专用状态清单扩展到通用文档。

### 7.5 工作指引的准确表述

- 用户任务成果放当前 Agent 的工作区；应用能力的长期资料放动态 state 子目录；一次性产物放动态 temp 子目录。
- Bash 缺省执行目录是当前工作区；相对 `working_dir` 也以当前工作区为基准。安装时可明确传入文档里的数据根绝对路径。
- `read` 等工具读取环境文件时使用提示词给出的绝对路径，不假设所有工具的相对路径规则相同。
- 共用 Python 既供应用运行，也默认供终端中的普通 Python 工作使用；改变终端目录不会自动切换 Python 环境。
- 受管独立环境只隔离 Python 依赖；使用其解释器的绝对路径调用脚本即可，不必激活环境或新增工具。普通 `python` 仍指向共用环境，不能把某个技能的解释器永久放到全局 PATH 最前面。
- pip 操作指明实际解释器，不使用可能落到宿主环境的裸 `pip`、`pip3` 或 Conda。
- npm 的 prefix / cache / 模块路径已在 Alpha 内；pnpm、yarn、Go 不被描述成已经完成相同收口。
- 服务变量按现有规则写入配置文件；路径策略由后端决定，不引导模型编辑 shell profile 或系统环境来改变 Alpha 布局。
- 描述当前 workspace、数据根和核心只读目录的规则，同时说明执行仍受现有命令分类、权限和操作系统限制。
- 不再使用“任何 `C:\Users\...` 都不能安装”这类粗略禁令。打包版合法数据根本来可能位于用户目录；应禁止写入 Alpha 管理范围之外的其他应用技能目录和普通文件位置。

### 7.6 文件写入、并发与失败

- 渲染完成后一次性写入，不边生成正文边供其他 Agent 读取。
- 采用临时文件加原子替换，临时文件放 `R/temp/runtime-info/`，使用每次写入独立的文件名；完成或失败后清理本次临时文件。
- 同一数据根的多个 worker 生成相同公共事实，不需要新增长期锁服务；原子替换避免读取半份文档。
- 不写会话级时间戳或 Agent 标识，以免相同事实每次生成不同内容。可以在内容相同时跳过替换。
- 写入失败时记录现有日志可见的简短诊断，不新建日志体系，不让普通对话因环境说明文件失败而完全不可用。
- 失败后不把旧文件当作本次有效结果：传给 prompt builder 的文档路径为空，提示词明确“环境说明文档本次不可用；不要猜测缺失的安装信息”。常用实际路径仍保留在提示词。
- 不回退写到宿主 HOME、程序资源目录或用户工作区；不在提示词内塞入整个文档作为隐藏的第二套维护逻辑。

## 10. Python 依赖决策与现有边界

### 10.1 决策顺序

| 条件 | 动作 |
| --- | --- |
| 纯文档技能或没有新依赖 | 正常安装技能目录，不新建环境 |
| 共用环境已满足所需版本 | 直接复用，不重复安装 |
| 新增依赖与现有环境兼容 | 安装进实际共用 Python |
| 新依赖与当前依赖无法共存 | 保留主环境；有 CLI 的工具可沿用 uv tool；脚本型技能在动态 `tools/venvs/<技能名>` 中创建独立环境并直接调用 |
| 网络、下载源、权限或工具缺失导致检查失败 | 报告具体失败，不能把这些故障当作依赖冲突或自动绕路 |
| 超出本次受管独立环境范围，仍要求新增后端工具 / 权限能力 | 报告应用接入需求；安装模型不自行修改注册表或权限实现 |

开发版和打包版使用同一决策顺序；差异通过实际布局和解释器路径体现，不按版本无条件强制隔离。

### 10.2 检查方式

- 使用已有 uv / pip 能力，不开发依赖解析器，不引入后台安装任务或长期依赖数据库。
- 在修改共用环境之前读取现有包和需求；依赖解析应覆盖连带依赖及当前应用已有依赖，不能只看新包名字是否存在。
- 共用环境安装必须保留全部当前已安装发行包版本作为临时约束，先做依赖解析 / 安装预演；中间文件放动态 temp 目录。约束不等于要求保留所有包，仍须检查预演是否包含已有包的删除、替换或重装。
- 只有预演仅增加兼容依赖时才能执行共用安装，使用同一解释器、需求、约束、配置处理和环境。最终检查与安装在第 10.2.1 节的同一次跨进程锁内完成，不依赖锁外快照检查。不能可靠表达现有包约束或读懂预演时报告检查不足，不猜测通过。
- 共用目标禁止 `--exact`、`sync`、卸载、升级和强制重装（含指定包版本形式），禁止 `--no-deps` 等绕过完整依赖解析的形式。安装参数检查必须识别操作语义及别名，不能只检查目标位置；实际执行共用安装必须带后端在锁内生成的当前版本约束，不能仅信任模型提供的旧约束文件。
- 安装技能可先通过终端检查需求；真正修改共用环境时，后端在同一次调用内生成最终约束并审核预演，命令校验负责目标和禁止操作。复用 uv / pip 的解析能力，不新增后台安装服务，也不声称命令沙箱能够限制任意 Python 代码内部的包修改。
- 在保留当前版本的条件下无法满足新需求，或预演需要删除、替换、重装已有包时，保留共用环境并转入第 10.3 节的独立环境流程，不能直接把技能判为不可安装；独立环境也无法满足时才说明阻碍。不为装技能升级、降级或卸载应用依赖。
- `pip check` / `uv pip check` 检查的是已安装环境，不可单独充当“未来安装不会冲突”的证明。安装后可用它确认依赖声明的一致性，不要求执行技能的完整业务流程。
- 若当前环境本就有依赖问题，区分既有问题与本次新增问题；不顺带修复整个项目环境。

以下列出检查与安装的命令形态；其中实际共用安装由后端按第 10.2.1 节保护执行，分开的 list / dry-run 调用不能替代锁内检查。以下仅为说明中可使用的命令形态，不是本次 PRD 编写要执行的安装命令；参数中的路径在实际任务中从文档解析，包名 / 版本来自用户指定来源：

```text
uv pip list --python "<共用Python绝对路径>"
uv pip install --python "<共用Python绝对路径>" --dry-run --constraints "<临时约束文件绝对路径>" <所需依赖>
uv pip install --python "<共用Python绝对路径>" --constraints "<同一临时约束文件绝对路径>" <所需依赖>
uv pip check --python "<共用Python绝对路径>"
```

uv 不可用时不能假装命令可执行；如果使用 Python 的 pip 模块，则显式指定共用解释器，并先确认该模块存在，且该版本能提供等价的约束与预演能力；无法满足则报告限制，不省略检查。具体引用方式遵循工具实际 shell，不把 PowerShell 语法直接塞给 Git Bash，也不使用未加引号的含空格路径。

### 10.2.1 共用安装的最小并发保护

技能安装以单 Agent 为主要场景，仅为偶发并发增加简单的跨进程文件锁；不做安装队列、调度器、后台服务、持久任务或让模型手动管理锁。

- **入口**：仍使用现有 Bash 工具。沙箱与参数检查通过后，`BashTool.execute()` 对支持的共用 Python 安装命令转入小型内部函数（建议 `agent/tools/python_install_guard.py`），普通命令保持原流程。不新增工具 schema 或注册项。只读 list / check / 单独 dry-run 不作为安装事务。
- **锁定范围**：同一次调用依次执行“取得锁 → 读取当前已安装包与依赖声明 → 生成版本约束 → 调用包管理器预演并确认只增加兼容包 → 用相同需求、约束和处理后的 env 安装 → 确认结束 → 释放锁”。锁内发现冲突即返回冲突原因，由安装技能转独立环境；不持锁等待模型再次回复。预演格式不支持可靠判断时停止，不猜测成功；复用包管理器解析，不自建依赖解析器。
- **锁位置**：锁文件固定为实际共用环境根下 `.alpha-skill-install.lock`，由选定解释器所属环境动态定位；同一环境的不同 Agent / 数据根得到同一个文件。环境身份保留 venv 根，不能把解释器最后一级链接解析到基础 Python 后把多个 venv 混为一个。无法确定或创建锁文件时报告限制，不跳过保护。此文件是安装协调元数据，不是用户临时产物。
- **实现方式**：参考 `browser_harness_lock.py` 中 Windows `msvcrt` / POSIX `fcntl` 的操作系统文件锁方式，使用独立的安装锁，不修改或占用浏览器锁。锁文件可保留，是否忙碌由操作系统锁判定，不能看到文件存在就当作占用，也不靠删除文件抢锁。
- **等待和退出**：默认最多等待 10 秒，且等待、预演、安装共用本次 Bash 的超时预算；不新增用户配置。等待时响应取消，超时返回“共用环境正在安装中，请稍后重试”。成功、失败均通过 finally 释放；取消 / 超时须先停止并等待安装子进程结束，再释放。不能保证终止时不得报告已安全完成。进程崩溃后的安装恢复不在本次承诺范围。
- **输入一致性**：锁内使用同一组已检查的参数及需求文件内容；内部生成的约束和必要输入副本放当前数据根 temp 的独立任务目录。实际安装前若输入变化则停止重新检查，不把预演和执行变成不同需求。
- **边界**：本次只保护应用支持入口的共用环境安装，不协调用户外部终端或任意 Python 代码的修改，不锁普通聊天、脚本运行或整个应用。普通独立环境按技能单独使用，本次不提供跨技能共享、并发写同一独立环境的保证，不扩展成通用环境管理系统。

### 10.3 受管独立 Python 环境：具体权限与执行设计

#### 10.3.1 当前真实调用链与拦截点

```text
模型调用现有 bash 工具
  -> ToolLoader.execute_tool()
       -> SandboxGuard.check_tool_call()
            -> _check_bash_command()
                 -> resolve_bash_command_context() 得到 command 与实际 cwd
                 -> 危险命令、显式输出 / 修改路径检查
                 -> classify_python_launcher_scope()
                 -> classify_package_install_scope()（依赖命令）
                 -> classify_alpha_venv_command_scope() / 脚本路径等后续判断
       -> deny：直接返回；ask：进入现有审批；allow：继续
  -> BashTool.execute()
       -> _prepare_command() 再次解析实际 cwd
       -> _validate_alpha_python()
            -> classify_python_launcher_scope()
            -> _resolve_alpha_python_launcher()，检查实际解释器是否存在
       -> build_runtime_env() 生成本次子进程环境
       -> subprocess.Popen(command, cwd=实际cwd, env=本次环境)
```

编写本节时，通过直接调用上述判断函数进行只读核对；下面的示例命令没有实际执行，也未创建环境或安装包：

| 命令形态 | 当前 sandbox | 当前终端预检 | 原因 |
| --- | --- | --- | --- |
| `"<R/tools/uv/browser-harness/Scripts/python.exe>" -c "pass"` | 拒绝 | 拒绝 | 独立解释器不属于目前认可的共用 Python |
| `uv pip install --python "<同一独立Python>" <包>` | 拒绝 | 不在直接 Python 预检范围 | 安装目标检查仍限定共用解释器 |
| `uv tool install <包>` | 允许 | 通过 | 已有独立工具安装分支 |
| `uv venv --python "<P>" "<R/tools/venvs/示例>"` | 一般命令允许 | 通过 | 创建命令目前无专用目标检查 |
| `uv venv --python "<P>" "<数据根之外的示例目录>"` | 也进入一般命令允许 | 通过 | 目标位置参数未作为环境写入目标识别 |

因此不是修改一条文字或一个 `if` 即可：需要同时对齐解释器允许范围、依赖目标、环境创建目标、终端预检和实际执行路径。

#### 10.3.2 指定目录与共用规则

复用动态数据根 `R`，使用以下两种环境目录：

| 环境用途 | 环境位置 | 创建方式 / 约束 |
| --- | --- | --- |
| 普通脚本型技能因依赖冲突需要隔离 | `R/tools/venvs/<技能名>/` | 使用 uv venv；只在确有依赖冲突时创建 |
| 已有或新安装的 uv CLI 工具 | `R/tools/uv/<工具名>/` | 沿用 uv tool 的目录与元数据，由 uv tool 管理 |

- 新建一个 `tools/venvs` 目录，是为了给普通虚拟环境确定明确位置；不要把手动 `uv venv` 创建的环境塞进 uv tool 的管理目录。
- 两种目录均从当前数据根动态拼接。建议在 `runtime_paths.py` 中用一个小函数返回这两个目录，供文档与权限判断复用，不新增环境注册数据库或每技能配置文件。
- `ensure_runtime_directories()` 可增加 `tools/venvs` 父目录；不在每次 Runtime 初始化时为每个技能创建环境。
- `UV_TOOL_DIR`、`UV_TOOL_BIN_DIR` 保持现有含义与保护规则；不增加可被模型任意覆盖的独立环境根变量。
- 开发版和打包版都将新增独立环境放在各自数据根。打包版无需改动程序资源目录来保存这些新环境。
- 共用环境判断与第 6.3 节的实际解释器选择对齐。独立环境判断作为明确的附加范围，不允许“只要在整个数据根或 workspace 下，就可以运行任意 python.exe”。
- 裸 `python` / `python3` 的缺省选择仍为共用环境。使用独立环境时必须明确给出对应解释器路径，推荐绝对路径。

#### 10.3.3 受管解释器识别

在 `command_path_extractor.py` 现有 Python 路径辅助函数附近收敛判断，不在 SandboxGuard 和 BashTool 中各维护一张不同的允许目录表。

建议保留现有内部返回值 `allowed_alpha_venv`，只扩展它的受管环境含义，避免为字符串重命名牵连整个权限体系。`_is_venv_python()` 可以改为委托一个含义清楚的公共识别函数；函数命名可调整，但以下判断必须一致：

1. 判断命令是否使用现有共用 Python；若是，保留原有允许规则。
2. 否则，按传入的实际 cwd 将解释器路径转为绝对路径；不能仍然默认为 `project_root`。
3. 判断该路径是否属于上述两个根下某个直属环境的标准解释器位置：Windows 为 `<环境>/Scripts/python.exe`，非 Windows 为 `<环境>/bin/python` 或 `python3`。
4. 环境名是单个目录名，不能为空、`.`、`..`，不能通过额外路径段跳到其他位置。
5. 新增独立环境的执行 / 包安装要求环境已经存在：具有 `pyvenv.cfg`，解释器是存在的文件，解释器所在目录和环境根匹配。仅在目录里随意放一个同名文件不能成为受管环境。
6. 目录边界使用规范化路径和路径层级关系，不能用字符串 `startswith`。`tools/venvs-other`、其他 Alpha 数据根、workspace 中的 `.venv`、temp 下的 Python、宿主 Python 都不因此获得允许。
7. 解析目录中的 `..`、链接 / Windows junction 后，受管环境目录仍须位于本实例数据根和指定目录内；指向外部目录的父目录链接不能通过。
8. 正常虚拟环境可能将最后一级 Python 文件链接到基础解释器。不能把整个调用路径 `resolve()` 成外部基础 Python 后再执行，否则会失去 venv 语义。保留环境内的调用路径；若最后一级文件是符号链接，仅接受其最终目标与当前共用 Python 对应的真实基础解释器一致的情况。普通文件则要求仍处于受管目录内。
9. `pyvenv.cfg` 的基础 Python 位置可在 uv 的基础 Python 安装目录；这不意味着模型可以直接调用那个宿主路径。环境识别依据受管环境入口，不能把配置中的 `home` 加入全局允许目录。

第 8 条用于避免正常 POSIX venv 的链接行为被误判；本次 Windows 为主要执行目标。若某种已有环境链接到另一套未认可的基础解释器，明确返回不支持，不能为了兼容它开放任意外部解释器。环境目录结构检查不是环境来源认证，也不是操作系统级文件沙箱。

#### 10.3.4 路径解析与命令识别统一

目前 `_resolve_executable_path()` 和 Bash 的 `_resolve_alpha_python_launcher()` 对相对解释器使用 project_root，但工具实际可能在 workspace 执行。本次涉及 Python 的分类 / 解析函数增加可选 `base_dir`，由 SandboxGuard 和 BashTool 传入同一份 `resolve_bash_command_context()` 得到的 cwd。

- 完整工具链必须传实际 cwd；辅助函数为兼容已有单元调用可保留 project_root 默认值，但不能让生产调用继续依赖该默认值。
- 在 workspace 执行 `.venv/Scripts/python.exe` 就只能指向 workspace 的 `.venv`；不能先按 Alpha 主环境通过检查，再执行另一个文件。
- 安装说明推荐绝对解释器路径；若需要相对路径，必须显式选择正确 working_dir。
- 对这次涉及的 uv 命令，`uv`、`uv.exe` 和带引号的绝对 uv 可执行路径需被归为相同命令类型。识别可执行文件名只用于选择检查分支，不新增“某个叫 uv.exe 的文件就是可信软件”的认证含义。
- `--python <路径>`、`--python=<路径>`、`-p <路径>` 的目标提取统一；缺失值、重复目标参数、不能解析的路径表达式不能选择性忽略或落到一般命令放行。
- 安装说明使用单条直接命令，不使用激活脚本、命令内 PATH 覆盖或多层 shell 包装。新增的环境创建入口只接收可明确解析的单命令形式；复合控制符要求拆成独立工具调用。
- 已有 `uv run --python` 的路径判断也要委托同一识别函数，终端不能把 `uv` 自身误当成待检查的 Python。按用户确定的范围，保留 uv run 的使用自由，不新增禁止自动同步或强制 `--no-project --no-sync` 的规则，不将它改写成直接 Python。第 10.2 节安装保护只覆盖明确支持的依赖安装入口，不承诺覆盖 uv run 自身的同步行为；本次不开发 uv 项目管理功能。

#### 10.3.5 创建独立环境的判断

推荐的安装命令形态如下，所有路径取自当次环境文档，且本次 PRD 阶段不执行：

```text
uv venv --no-project --no-config --no-python-downloads --python "<共用Python绝对路径>" "<R/tools/venvs/技能名>"
uv pip install --python "<独立环境Python绝对路径>" -r "<技能已有requirements文件绝对路径>"
"<独立环境Python绝对路径>" "<技能原脚本绝对路径>" <原有参数>
```

没有 requirements 文件时按原有依赖声明传包参数，不要求给每个技能新增 requirements。uv 创建的环境不保证预装 pip，优先继续使用 uv pip，不为能执行 `python -m pip` 而额外下载一套安装工具。

具体检查：

- 为 `uv venv` 增加专用目标识别，不能沿用一般未知命令的默认允许。目标必须明确为 `R/tools/venvs/<名称>`，源 Python 必须明确为本实例已认可的共用解释器，避免 uv 自动选取或下载另一套 Python。
- 创建目标与执行目标是两种检查：创建时目录可以不存在，不要求 `pyvenv.cfg` 已存在；执行 / 安装包时必须验证已形成真实环境。
- 目标已是完整受管环境时复用，不执行清空重建；目标存在且非空但不是有效环境时报告冲突，不覆盖未知内容。
- 不接受 `--clear`、`--allow-existing`、`--system-site-packages` 等改变本次新建 / 隔离边界的选项，不接受 `--directory`、`--project` 等让工具悄悄改变判断基准的选项；对未支持的创建选项返回明确说明。
- 不能省略创建目标而让 uv 默认在 workspace 生成 `.venv`。不能在 `tools/uv` 中手工创建普通技能环境，也不能在指定根之外创建。
- 同时识别 `"<认可Python>" -m venv <目标>` 的环境创建语义，防止它直接落到现有 `project_command` 的一般允许分支。若使用此形式，目标、已有目录、隔离选项沿用同一判断；安装说明仍优先使用 uv。
- 环境创建的允许判断放在危险命令、显式写入路径检查之后、普通 project / unknown 放行之前。返回明确的 allow / deny；失败不能改成让用户审批任意越界目标。
- 不为本次功能增加自动修复 uv、下载基础 Python 或迁移主环境的流程；现有工具缺失时报告原因。

建议在 `command_path_extractor.py` 新增一个小的创建命令识别 / 目标检查函数，返回“非创建命令 / 允许 / 拒绝及原因”。SandboxGuard 与 BashTool 预检复用它，不新增通用命令解析框架。可将受识别的创建命令纳入现有依赖类并分派给该函数，不必修改 `BashCategory` 增加一套分类体系。

#### 10.3.6 依赖安装目标的判断

- `_classify_uv_pip_install()` 的 `--python` 目标，从只认可共用解释器扩展为“共用解释器或已经存在的 tools/venvs 下普通技能独立解释器”；tools/uv 中的解释器可以调用，但不能作为普通技能 pip / uv pip 安装目标。
- `"<受管独立Python>" -m pip install ...` 沿用同一判断；pip 模块不存在时由正常执行结果报告，不能回退到宿主 pip。
- `uv pip install` 缺少明确解释器仍拒绝；裸 `pip`、`pip3`、`pip3.12` 等仍拒绝。
- `--user`、`--system` 继续拒绝。对于这次认可的 Python 安装命令，`--target`、`--prefix`、`--root` 等另选写入目的地的选项也不得绕开选定环境；识别空格和等号形式，提示使用明确环境目标。
- `--python` 的有效性不是整条命令自动放行的理由：命令中的显式输出重定向、越界写入参数继续先检查。
- 共用目标同时执行第 10.2 节的操作限制，不能因为目标正确就允许 exact / sync / 卸载 / 重装。独立目标不套用主环境的版本约束，但本次技能安装仍只做所需依赖安装，不自动清空、同步删除或重建既有环境。
- uv tool 的现有安装与入口方式保留；普通脚本环境不伪装成 uv tool 包，不新增工具注册。
- 普通独立环境按技能复用自己的已有安装；本次不新增跨技能共用独立环境或自动合并依赖。tools/uv 中已有工具的复用仅指调用能力，不表示允许其他技能修改它的依赖；其维护仍归原有工具安装方式。普通技能安装不得执行对 Browser Harness 的重装、升级、卸载或追加依赖。

#### 10.3.7 终端预检与子进程环境

`BashTool._prepare_command()` 应把本次 cwd 传入共用校验；`_validate_alpha_python()`、`_resolve_alpha_python_launcher()` 与 sandbox 使用同一允许范围和同一个实际解释器。

**直接 Python 调用：检查哪个，就执行哪个，不改变模型明确选择的合法环境。**

- 对可明确识别的单条直接命令，裸 `python` / `python3`（含平台对应的 `.exe` 名称）表示使用第 6.3 节解析的共用 Python。后端将命令入口绑定为该已校验解释器的绝对路径，不能仅把其目录放在 PATH 后就执行原始裸名称，避免 cmd 优先执行工作区同名程序。
- 明确给出合法共用 / 受管独立解释器路径时，使用模型指定的入口；相对路径按本次实际 cwd 定位后固定为绝对调用路径。不得把明确指定的独立环境替换成共用环境。保留虚拟环境内的启动入口，真实路径解析只服务边界判断，不能把链接入口换成基础解释器。
- 将现有“校验后只返回是否有错误”的链路调整为：共用解析函数得到调用入口 → sandbox 校验解释器、脚本与显式输出路径 → Bash 复用解析结果完成预检 → `_prepare_command()` 返回实际执行命令及已校验入口 → `execute()` 执行该入口。保留用户原命令用于结果说明，不能执行未经检查的另一个入口。
- 只替换明确识别出的命令开头的解释器 token，使用实际 shell 对绝对路径正确引用，后续参数原文保持不变；禁止对整段命令全局替换 `python`。脚本参数、`-c` 中的代码字符串、嵌套命令均不能被误改。无法可靠识别或引用的直接 Python 组合命令返回拆分指引，不猜测转换；此限定不用于禁止 uv run。
- 解释器不存在、环境不完整或不在允许范围时明确报错，不回退共用或宿主 Python。不新增工具、配置开关、环境激活步骤，也不新增允许的环境范围。此绑定只保证本次直接命令入口，不承诺接管脚本内部自行启动的所有进程。

- 显式指定独立 Python 时，检查的文件就是随后执行的那个入口；文件缺失或环境结构不完整时返回对应路径和原因，不能改用主环境或宿主 Python。
- 保留环境内入口路径，不将链接入口重写成基础 Python；含中文和空格的路径按实际 shell 正确引用。
- 对明确调用受管独立 Python 的命令，先生成现有 `build_runtime_env()`，再仅在此次 `Popen` 的环境字典中设置 `VIRTUAL_ENV=<该环境>`，将该环境的 `Scripts` / `bin` 放到该次 PATH 前面并去重。这样脚本内部常规子进程也优先使用同一环境。
- 上述调整由后端依据已校验路径完成；不修改 `os.environ`，不保存到 `runtime_env.local.json`，不要求模型执行 `activate` 或自行覆盖 PATH。
- HOME、state、temp、cache 等仍指向 Alpha 原有运行目录。依赖隔离不意味着创建另一套用户资料目录。
- 普通共用 Python 命令和下一次未指定独立环境的调用仍使用共用环境；两个 Agent 的命令不会通过全局 PATH / VIRTUAL_ENV 相互切换环境。
- `uv pip --python ...` 根据已校验的显式目标安装，不靠父进程 VIRTUAL_ENV 猜测目标；创建环境的源解释器仍是共用 Python。
- 不把某个独立环境永久加到全局 PATH，也不将它设置成应用后端解释器。

**创建 / 安装命令的环境与配置处理：**

- 在 `build_runtime_env()` 合并宿主环境与服务配置之后、`Popen` 之前，对识别出的创建 / 安装命令复制并处理本次 env。不能只过滤 `runtime_env.local.json`，因为同名变量也可能来自宿主。普通业务命令与持久配置不受此清理影响。
- 对本次支持的 uv 命令，移除继承的 `UV_VENV_CLEAR`、`UV_VENV_SEED`、`UV_WORKING_DIR`、`UV_PROJECT`、`UV_CONFIG_FILE`、`UV_PYTHON`、`UV_SYSTEM_PYTHON`、`UV_BREAK_SYSTEM_PACKAGES`、`UV_CONSTRAINT`、`UV_OVERRIDE`、`UV_EXCLUDE`、`UV_BUILD_CONSTRAINT`、`UV_NO_BUILD_ISOLATION` 等会改变目标、清空、需求或隔离行为的变量；Python 下载策略固定为禁止自动下载。实施时按实际支持 uv 版本核对同类变量，不能把这组示例当作永远完整的清单。
- uv 创建 / 安装统一禁用配置文件读取（`--no-config`），禁止命令再提供 `--config-file`、`--directory`、`--project` 及相应重定向形式。`--no-config` 不负责清除环境变量，二者分别处理。需求 / 约束文件若含改变安装策略的选项也按同样规则检查，不把它们当作无条件可信输入。
- Python `-m pip` 的等价路径处理 `PIP_TARGET`、`PIP_PREFIX`、`PIP_ROOT`、`PIP_USER`、`PIP_PYTHON`、`PIP_CONFIG_FILE`、`PIP_CONSTRAINT`、`PIP_REQUIREMENT`、`PIP_NO_DEPS`、`PIP_IGNORE_INSTALLED`、`PIP_FORCE_REINSTALL` 等相关变量，并将本次 `PIP_CONFIG_FILE` 设为平台空设备，禁用配置文件读取；明确目标与约束只来自已检查的命令。具体参数以项目实际 pip 版本支持为准，不支持等价处理时返回限制。
- 保留正常服务变量、下载源、认证、代理和证书设置，不一刀切删除全部 `UV_*` / `PIP_*`，也不在文档或错误中输出敏感值。原来仅存于被禁用配置文件中的必要源设置，应明确诊断并使用现有服务配置入口提供，不能静默换源。
- shell 内 `env KEY=...`、变量赋值等可重新覆盖这些设置的组合，不进入受支持的安装允许分支；提示拆成明确的单条命令。沙箱和 Bash 预检复用语义识别，最终执行必须使用处理后的 env，预演与实际安装应用同一处理。

#### 10.3.8 保持的权限边界与检查顺序

1. `ToolLoader.execute_tool()` 的 sandbox → ask 时审批 → 工具执行顺序不变，`enable_permissions=False` 也不能绕过 sandbox 的 deny。
2. 危险系统命令、显式越界输出、`agent` / `session-log` 的只读规则保留；本次不修改 `path_policy.py` 的全局文件访问范围。
3. 宿主 / Conda / 其他项目解释器、Windows `py` 启动器、命令内 PATH 覆盖仍按原规则拒绝；认可某个独立环境不等于开放它使用的所有外部路径。
4. 直接 Python 执行脚本时，允许当前 workspace、Alpha 数据根，以及 Runtime 实际加载的内置技能目录中的脚本。`ToolLoader` 已持有 `skills_dir`，应将其作为 `builtin_skills_dir` 明确传给 `SandboxGuard`（及需要同样预检的 Bash），不推测 cwd、不开放整个程序根。规范化实际路径后确认目录包含关系，内置目录中的链接不能扩大允许范围。此目录只增加执行许可，不增加额外写权限，仍沿用现有文件策略：开发版 skills 在数据根内，当前并非统一只读；打包版资源目录不因此加入可写根。本次不新增内置目录只读拦截；不能让新增的 `_is_venv_python_or_cli()` 允许分支在脚本路径检查之前提前放行。`extract_script_path()` 需识别带绝对路径的受管 Python，不能只认裸 `python`。
5. `-m <模块>` 和 `-c <代码>` 使用明确受管解释器时允许，与现有共用 Python 的使用含义一致；不开发 Python 代码内容白名单。
6. 受管环境中的 Python、环境创建和安装命令不得在识别失败后作为“未知外部 CLI”放行。错误要说明失败的是目标目录、解释器、环境不完整还是参数形式。
7. 本次不新增任意独立环境 CLI 的特别信任范围；已有 uv tool / bin 命令沿用原规则。通用脚本直接通过 Python 调用即可。
8. 这仍是命令 / 路径级的现有 sandbox，不是操作系统级进程隔离。允许 Python 执行没有新增“可以保证检查脚本内部所有文件写入”的承诺。

- 第 10.3 节会统一调整应用层对受管环境的允许判断；这不等于修改 Windows 文件权限。实际安装遇到工具不可用、操作系统权限拒绝或环境不可写时，说明具体原因，不修改 ACL、不迁移主 Python，也不新增第三方依赖的升级保留机制。
- 打包版创建独立环境时使用随包共用 Python 作为明确的基础解释器，目标在数据根；如果随包基础 Python 不满足 venv 创建条件，报告具体错误，不自动改包或下载另一套 Python。基础解释器适用性不通过本次文档阶段的真实安装演练验证。
- 不执行真实 EXE 安装、卸载、升级或依赖安装演练。

明确保持不变：SkillLoader 扫描 / 优先级 / 缓存、ToolLoader 工具注册、Bash working_dir 的现有 workspace 语义、全局文件访问边界、审批机制、MCP 注册、Browser Harness 专用链路、Electron / EXE 打包、前端与 API、Agent Loop、协作和记忆角色。改变的是受管 Python 相关判断，不是整体关闭 sandbox。

## 14. 验收与测试边界

### 14.1 必须满足的验收标准

| 场景 | 预期结果 |
| --- | --- |
| 开发布局设置解释器覆盖；另一个数据根 | 前者文档、终端 PATH、默认 Python 与沙箱一致采用覆盖；后者不借用覆盖 |
| 打包版 Python 不在 Scripts 中 | 公布独立 CLI 目录并加入子进程 PATH；不存在的入口不宣称可用 |
| 程序根与数据根分离的 DOCX / PPTX 脚本 | 完整 AgentRuntime 初始化（含 configure_runtime）后实际内置 skills 脚本仍可执行；执行许可不改变既有写权限，程序根其他脚本不获新增许可 |
| 宿主 / 服务配置含 UV_VENV_CLEAR、UV_WORKING_DIR、UV_CONFIG_FILE 或 pip 重定向 | 假 Popen 收到处理后的 env；创建 / 安装目标不偏移；普通服务变量与普通命令不被误清理 |
| 配置文件或命令内赋值重新覆盖安装行为 | uv / pip 配置入口禁用，未支持的覆盖形式拒绝，预演与安装处理一致 |
| 共用目标使用 --exact / sync / 强制重装，或内部无法生成有效约束 | 明确拒绝；预演要求删除 / 替换现有包则转独立环境，不修改主环境 |
| 共用目标预演只增加兼容包 | 复用共用环境；最终在锁内读取当前包、重新预演并安装，不默认创建独立环境 |
| 两个进程安装同一共用环境 | 第二个等待，第一个结束后重新读取依赖并检查；无法兼容时不修改共用环境 |
| 安装锁忙碌、取消、预演失败、安装超时 | 返回准确状态，不绕过锁；子进程结束后释放锁，无遗留安装继续运行 |
| 普通技能向 tools/uv/browser-harness 或其他 uv tool 环境安装包 | 拒绝修改；已有解释器调用规则与 Browser Harness 专用执行器保持 |
| 本次新建独立环境后成功或失败 | 用户均获知创建原因、实际位置、调用方式及准确状态；不新增审批 |
| 工作区有同名 python.exe，终端使用 cmd；Git Bash 对应用例 | 裸 Python 最终执行共用解释器绝对路径，不执行工作区同名程序；用假 Popen 验证实际命令 |
| 模型明确指定合法独立 Python，或该文件不存在 | 前者执行指定环境，不改为共用；后者明确报错且不启动替代解释器 |
| 含空格 / 中文的解释器路径，参数或 -c 字符串含 python 字样 | 仅命令入口正确引用并绑定，后续参数内容保留；无法可靠处理的组合返回拆分指引 |
| uv run 调用 | 保留现有使用方式，不因直接 Python 入口绑定而被改写或新增 no-sync 限制 |
| 普通开发布局 | 文档在实际数据根的 state 下；Python 与现有终端默认解释器一致 |
| 程序根 / 数据根分离 | 内置技能指向程序根，第三方技能 / 文档 / temp / state 指向数据根，Python 指向已配置解释器 |
| 数据根含中文和空格 | 文档能按 UTF-8 读回；提示词提供完整绝对路径，不出现未展开占位符 |
| worker cwd 在外部 workspace | 文档仍写入数据根；不在 workspace 创建另一份 runtime-info.md |
| 同一 Alpha 的两个普通 Agent | 公共文档不包含任一 Agent 的 workspace / ID；各自提示词仍保留自己的 workspace |
| 两个不同数据根 | 分别写入自己的文档，不泄露或复用上一个根的路径 |
| 环境中混入 API Key、Cookie、代理凭据等 | 文档只含公开集合，敏感值和自定义服务变量原文不会出现 |
| 文档写入失败 | 不引用旧文件为有效文档；短提示说明不可用；不回退到其他目录，不导致整个普通对话必须失败 |
| 安装说明 | 正确描述实际目录与受管 Python 范围，普通技能依赖兼容则共用、冲突才隔离 |
| 第三方技能 MD 适配 | 仅修改路径和调用指令；工作流程、行为要求、输出要求、名称 / 描述及其他内容保持原样 |
| 独立脚本型技能 | 在指定目录形成有效环境后，通过现有 bash 直接调用其 Python 和原脚本，不新增后端工具或包装脚本 |
| 环境创建与依赖安装 | 创建位置、基础解释器和安装目标都可明确判定；越界目标或不完整环境不会因一般命令分支被放行 |
| 多 Agent 执行不同 Python | 本次子进程得到对应环境；后续普通调用仍为共用 Python，全局环境不被改写 |
| 安装后用户反馈 | 提示新建对话并发送“请检查「技能名称」是否安装成功。”，不附带长篇验证模板 |
| 其他能力 | 不增加工具、API、前端页面或技能热加载；外部 Python、越界写入、核心只读和审批机制保持限制 |

### 14.3 独立环境必须覆盖的边界矩阵

以下场景可参数化合并，不要求每一行单独新增测试文件：

| 场景 | 预期 |
| --- | --- |
| 开发版共用 Python、打包版配置 Python、有效 `tools/venvs/<名>`、有效 `tools/uv/<名>` | 执行范围通过共同判断；安装仅允许共用与 tools/venvs 目标，tools/uv 不获普通依赖修改许可；Browser Harness 专用执行器不受修改 |
| 环境缺少 `pyvenv.cfg`、缺少解释器、同名路径是目录、环境目录只有无关文件 | 执行 / 安装拒绝，错误准确；没有主环境或宿主回退 |
| 宿主 Python、其他 Alpha 实例、workspace `.venv`、temp Python、`venvs-other` 相邻目录 | 不属于新增允许范围 |
| `..` 路径逃逸、受管父目录 junction / symlink 指向外部 | 拒绝；合法最后一级解释器链接按第 10.3.3 节单独判断 |
| workspace 与 Alpha 都有同名相对解释器位置 | 按实际 working_dir 解析；不允许检测到 Alpha 的文件却执行 workspace 的文件 |
| 中文空格路径、原生 Windows / 已支持 MSYS 路径、带引号的绝对 uv.exe | 解析和执行路径一致；不同 uv 拼写不会退到未知命令绕过检查 |
| uv venv 创建允许的未存在目标；省略目标；目标越界；目标已有非环境文件 | 前者允许，其他拒绝或报告占用；不删除原文件 |
| uv venv 的 `--clear`、`--system-site-packages`、目标 / Python 重复参数、控制符复合命令 | 不进入本次受管创建允许分支，给出明确拒绝或拆分指引 |
| uv pip install 的受管目标 / 外部目标、`-p`、`--python=`、裸 pip、`--target` / `--prefix` / `--root` | 有效受管目标通过，外部或重定向目标拒绝；参数写法不改变边界 |
| 认可 Python + 允许范围内脚本；认可 Python + 范围外脚本；认可 Python + 越界输出重定向 | 前者通过，后两者仍拒绝，不能被解释器允许分支提前放行 |
| 单个独立调用后再执行共用调用；两个 Agent 分别选不同独立环境 | 假 Popen 收到各自的 cwd / PATH / VIRTUAL_ENV；`os.environ` 与持久配置不改变 |
| 权限模式 auto 或关闭额外询问 | sandbox deny 仍然拒绝；没有把被禁止目标变成人工同意即可执行 |

此处验证的是待实施代码的解析与调用契约，不是验证真实技能安装成功；用户的真实安装验证仍采用一句提示词的新对话方式。
