# 管理知识库 Wiki

## 核心原则

把用户确认过的资料整理成可查询、可追溯、可持续更新的本地 Markdown Wiki。一个项目可以是单领域、多领域或不断长出新领域的个人知识库，不要求预设单一主题。保持最小依赖：只使用 Agent 已有的查找、读取、写入、编辑、移动和联网工具；不引入 qmd、BM25、向量数据库、RAG 服务或 Obsidian。

## 触发门槛

只有用户明确点名本 Skill 或由产品按钮发送明确调用指令时才执行。

普通聊天、上传文件、阅读文档、联网搜索和发现项目里有很多资料，都不能自动触发知识库初始化、转换或更新。

## 操作模式

| 用户意图 | 模式 |
|---|---|
| 把已有项目整理成知识库 | 转换已有项目 |
| 在空文件夹新建知识库 | 初始化空项目 |
| 问知识库中的问题 | 只读查询 |
| 把指定文档加入知识库 | 新增资料 |
| 搜索或下载新资料 | 搜索与暂存 |
| 删除知识库中的资料 | 归档资料 |
| 指出 Wiki 内容有误 | 用户审阅 |
| 检查知识库健康度 | 巡检 |
| 全面整理知识库 | 全库整理 |

如果用户没有说明模式，根据明确请求选择；不确定时只问一个最关键的问题。

## 固定目录

知识库只固定以下最小结构：

```text
AGENTS.md
inbox/
raw/
wiki/
├─ index.md
├─ log.md
└─ sources/
archive/
├─ raw/
└─ wiki/
```

根据实际资料决定是否创建主题目录和综合页面。不得照搬固定领域模板，不得为了填满结构创建空目录或空页面。

## 生成 AGENTS.md

初始化或转换知识库时，必须在项目根目录生成新的 `AGENTS.md`，让后续普通会话自动遵守知识库规则。

### 处理已有 AGENTS.md

如果根目录已存在 `AGENTS.md`：

1. 查找第一个未占用的备份名：`AGENTS-1.md`、`AGENTS-2.md`、依次顺延。
2. 将用户原有的 `AGENTS.md` 改名为该备份名，不删除、不覆盖。
3. 创建新的知识库 `AGENTS.md`。
4. 明确告诉用户：
   - 原文件保存在哪个备份名；
   - alpha 只自动加载根目录中名为 `AGENTS.md` 的文件；
   - 备份文件不再自动生效；
   - 如需恢复原规则，可由用户明确要求恢复。

不得把新规则追加到旧 `AGENTS.md` 后面，也不得静默覆盖旧文件。

### 新 AGENTS.md 的必备内容

根据当前项目生成简洁、项目专属的规则，至少包含：

1. **知识库范围**
   - 当前覆盖的主要领域；如果尚未形成领域，则说明这是开放的个人知识库；
   - 已确认入库的资料范围；
   - 明确排除的内容。
2. **目录职责**
   - `raw/` 是已确认的原始资料层；
   - `wiki/` 是 Agent 维护的知识层；
   - `inbox/` 是尚未入库的暂存层；
   - `archive/` 是退出活跃知识库但可恢复的归档层。
3. **原文保护**
   - 不改写、覆盖或删除 `raw/` 中的用户资料；
   - 移动资料时保持附件和相对链接有效。
4. **查询规则**
   - 普通问答先读 `wiki/index.md`；
   - 再读相关综合页和 `wiki/sources/`；
   - 必要时回查 `raw/`；
   - 明确区分库内知识、Agent 推断和知识缺口；
   - 普通问答默认只读。
5. **写入规则**
   - 只有用户主动要求整理、加入、修订或归档知识时才修改 Wiki；
   - Agent 可以询问是否保存，但不得默认保存。
6. **来源规则**
   - 区分原始资料、格式副本、翻译、二次分析、笔记、讲稿和 Agent 推断；
   - 同一来源的多个格式不计为多份独立证据；
   - 综合结论必须可追溯到资料摘要和原文件。
7. **联网规则**
   - 只有用户要求联网时才搜索；
   - 搜索结果不自动进入知识库；
   - 下载文件先进入 `inbox/`。
8. **更新规则**
   - 新增、审阅、归档和巡检后更新 `wiki/index.md`；
   - 向 `wiki/log.md` 追加记录，不重写历史。

生成完成后，提醒用户新建会话。alpha 只在会话创建时自动加载根目录 `AGENTS.md`。

## 转换已有项目

### 1. 只读盘点

先扫描项目，不修改文件。将文件归为逻辑资料组，而不是逐文件计数。

默认分类：

| 分类 | 默认处置 |
|---|---|
| PDF、Markdown、TXT、HTML、Word等知识文档 | 建议入库 |
| 同一资料的PDF、TXT、翻译、配套图片和数据 | 合并为逻辑资料组或配套文件 |
| 代码、日志、会话复盘、临时文件、配置、生成脚本 | 建议不入库 |
| Skill草案、AGENTS备份、知识库说明 | 管理文件，不入库 |
| 无法判断用途或来源的文件 | 建议暂不归类；只有是否入库本身无法判断时才询问用户 |

检查移动是否会破坏图片、附件或相对链接。保持相关目录结构或一起移动配套文件；不得通过改写原文来掩盖路径问题。

### 2. 转换预览

在一个紧凑回复中提供：

- 推断的主要领域和资料类型；资料跨度较大时说明这是多领域个人知识库，不强行概括成单一主题；
- 建议入库的逻辑资料组；
- 建议排除的内容；
- 配套文件和重复格式；
- 待用户判断的内容；
- 建议的最小 Wiki 结构。

给出默认推荐，允许用户回复“按默认方案继续”。用户没有确认前，不得移动文件、生成 Wiki 或替换 `AGENTS.md`。

### 3. 执行转换

用户确认后：

1. 创建最小目录。
2. 将确认入库的资料和必要附件移动到 `raw/`；不按主题反复移动原文。
3. 将不入库内容留在原位置。
4. 按逻辑资料组创建简短的 `wiki/sources/` 摘要。
5. 根据资料实际关系创建必要的综合页；资料不足时只保留摘要。
6. 创建或更新 `wiki/index.md`。
7. 创建 `wiki/log.md` 并记录转换。
8. 按前述规则备份旧 `AGENTS.md` 并生成新的 `AGENTS.md`。
9. 验证所有移动目标、Wiki页面和Markdown相对链接。

每个资料摘要至少说明：

- 资料身份与类型；
- 对应的 `raw/` 文件；
- 核心内容；
- 来源和可信度边界；
- 与现有知识的关系；
- 需要进一步验证的内容。

同一论文的PDF、TXT、翻译可以归入同一个逻辑资料组，但必须分别标明“原文、格式副本、翻译”。二次分析是独立表达层，不得冒充原论文。

讲稿、笔记或二次分析即使引用顶级期刊，也不继承原论文的可信度。没有逐项对照原文时，不得声称“忠实还原”“已经验证”或把资料标为原始论文级证据。

## 混合主题与结构演化

把分类当作导航，不当作检索边界。使用以下克制规则：

1. `raw/` 负责保存来源，不强制按主题分文件夹。一份资料可以同时关联多个领域。
2. 每份资料先建立 `wiki/sources/` 摘要，并在摘要或索引中记录少量领域、资料类型和必要标签。
3. 主分类保持少而稳定。会议纪要、阅读笔记、研究资料等资料类型可以作为导航；金融、人工智能等内容主题优先使用标签和页面关联，不因每份新资料创建一级分类。
4. 当至少两份资料共同支持某主题、单份资料本身足够形成独立领域，或用户明确要求时，才创建主题页。资料不足时只保留摘要和索引标签。
5. 无法可靠分类的资料标为“暂未归类”或“跨领域资料”，继续进入索引并保持可查询；以后获得更多上下文时再调整。
6. 资料明确支持的跨主题关系可以写入相关页面。AI 推测的潜在关系只能标为“待验证关联”或“待探索问题”，不能写成正式结论。
7. 重复资料保留各自来源，在综合页合并表达；真实冲突并列双方观点、来源、时间和证据边界，不武断选择一方。
8. 新增和归档时只维护直接受影响的页面。添加标签、修复导航和合并明显重复等小调整可直接执行；新增或删除一级分类、大量移动 Wiki 页面、拆分或重写多个综合页时，先给出一次整体预览并等待确认。

目录和页面结构应随资料自然生长，不为单领域预建复杂模板，也不为多领域预建一套固定分类法。

## 初始化空项目

1. 确认项目为空或没有待转换资料。
2. 不强制用户预设主题。用户没有指定时，默认初始化为开放的个人知识库；已有明确学习方向时，只把它记录为当前关注领域，不设为永久边界。
3. 创建最小目录、空索引和日志。
4. 按规则处理已有 `AGENTS.md`，生成新的知识库 `AGENTS.md`。
5. 不创建领域主题目录；等资料加入后再判断。
6. 告诉用户把待选资料上传或下载到 `inbox/`，或明确要求加入知识库。
7. 提醒用户新建会话。

## 产品知识库标识

初始化空项目或转换已有项目时，`.alpha/knowledge-base.json` 是产品识别知识库身份的唯一标识。它不是知识内容，不进入 `wiki/index.md`，也不写入任何资料摘要。

只有以下事项全部完成后，才最后创建 `.alpha/knowledge-base.json`：

1. 已确认入库的原始资料已经移动到 `raw/`，且文档内容没有被修改。
2. Wiki、资料摘要、`wiki/index.md` 和 `wiki/log.md` 已创建或更新完成。
3. 根目录知识库 `AGENTS.md` 已生成，原有 `AGENTS.md` 已按规则备份。
4. 所有移动目标、Wiki 页面和 Markdown 相对链接已经验证。

创建时遵守以下规则：

- `.alpha/` 不存在时创建它；已经存在时只新增标识文件，不覆盖 `.alpha/` 中的任何其他文件。
- 标识固定写为以下 JSON，其中 `created_at` 使用实际完成时间的 ISO 8601 字符串：

```json
{
  "type": "knowledge_base",
  "version": 1,
  "created_at": "2026-07-23T12:00:00+08:00"
}
```

- 创建标识必须是本次转换的最后一个写入动作。标识创建后只做只读确认，不再修改其他项目文件。
- 用户取消、尚在等待确认、权限失败、任一步骤报错或转换中断时，不得创建标识。
- 项目中已有部分 Wiki 时，先重新盘点并补齐缺项，不盲目覆盖；只有全套验证完成后才创建标识。
- 标识已经存在时，不重写 `created_at`，按现有知识库进入新增、归档、审阅或整理流程。

## 只读查询

普通问答按以下顺序：

1. 读取 `wiki/index.md` 定位知识。
2. 根据问题读取一个或多个相关领域、综合页和关联页面；分类只用于导航，不限制全库查询。
3. 需要来源细节时读取 `wiki/sources/`。
4. 需要核实原意时读取 `raw/`。
5. 回答时标明依据的 Wiki 页面或原始资料。
6. 如果知识库没有覆盖，明确说明缺口；不得用模型自身记忆伪装成库内知识。

查询不修改 Wiki。只有用户主动要求保存知识时才进入新增或审阅流程。Agent 可以在回答末尾简短询问是否保存，但不能默认写入。

## 搜索与暂存

1. 只有用户明确要求联网时才搜索。
2. 先在对话中展示搜索结果和来源，不自动创建文件。
3. 用户要求下载时，将文件保存到 `inbox/`。
4. `inbox/` 内容不是活跃知识来源，普通问答不得默认引用。
5. 用户明确选择加入后，转入新增资料流程。

## 新增资料

先检查文件身份、重复格式、附件、来源和与现有结论的关系。

### 简单新增

如果文件身份明确、无重复、无重要冲突，且只影响一个摘要和少量页面，用户“加入知识库”的请求本身就是授权。直接：

1. 将文件及必要附件从 `inbox/` 或根目录移动到 `raw/`。
2. 创建或更新一个资料摘要。
3. 更新确实受影响的综合页。
4. 更新索引并追加日志。
5. 验证链接。

### 关键新增

如果存在以下任一情况，先给简短预览并等待确认：

- 来源不明；
- 疑似重复；
- 与现有结论冲突；
- 需要移动多份配套文件；
- 会修改多个综合页面；
- 无法判断资料类型或可信度。

预览说明计划移动的文件、拟新增摘要、受影响页面和冲突处理方式。

## 归档资料

用户说“删除知识库中的资料”时，默认执行可恢复归档，不物理删除。

执行前必须：

1. 找到完整逻辑资料组和配套文件。
2. 列出依赖该资料的摘要、综合页和结论。
3. 说明归档后准备撤回或降级的内容。
4. 等待用户确认。

确认后：

1. 将原始资料移入 `archive/raw/`。
2. 将对应资料摘要移入 `archive/wiki/`。
3. 从活跃索引中移除该资料。
4. 删除、改写或降级仅由该资料支持的综合结论。
5. 保留仍有其他来源支持的内容，并更新来源说明。
6. 追加日志，记录影响范围和归档路径。

## 用户审阅

用户批评 Wiki 时，先判断批评类型：

- 事实或来源归属：回查相关摘要和 `raw/`，判断批评成立、部分成立或不成立。
- 结构、表达或关注重点：检查对其他页面和链接的影响。

先报告核查结果、拟修改位置和连带影响，再等待确认。不得为了迎合用户而无痕覆盖资料事实。修改后更新受影响页面、索引和日志。

## 巡检与全库整理

只有用户明确要求“巡检”“整理知识库”“全面整理”，或产品按钮发送对应指令时，才执行全库检查。普通问答和单份资料新增不触发全库整理。

检查：

- 失效相对链接；
- 无来源或来源等级写错的结论；
- 同源资料被重复计为独立证据；
- 新资料加入后仍未更新的综合页；
- 归档资料仍残留在活跃结论中；
- 重复、孤立、空洞或过度拆分的页面；
- 分类是否过细、过早固定或不再适合现有资料；
- “暂未归类”资料是否已经具备可靠归属；
- Wiki覆盖不足却使用确定语气的结论。

验证相对链接时，从“链接所在Markdown文件的目录”解析目标，不能统一从 `wiki/` 根目录解析。

失效链接、明显重复索引、缺少反向导航等低风险问题可以直接修复。涉及一级分类变化、大量页面移动、多个综合页拆分合并或整体组织方式变化时，先报告原因、方案和影响范围，等待用户确认。完成后追加日志。

## 完成报告

每次写操作完成后，简短报告：

- 移动、创建、修改和归档的文件；
- 更新的 Wiki 页面；
- 未处理或待确认事项；
- 原文是否保持未改；
- 链接验证结果；
- 初始化或转换时，产品知识库标识是否已在最后创建；
- 是否需要新建会话。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 看到很多文档就自动建库 | 只有显式调用才启动 |
| 用第一篇资料决定整个目录 | 先盘点全项目，再给转换预览 |
| 要求用户先给知识库确定单一主题 | 默认允许开放的个人知识库，领域随资料生长 |
| 按主题反复移动原始资料 | 原文保留在 `raw/`，主题关系由摘要、索引和 Wiki 页面表达 |
| 每新增一种内容就创建一级分类 | 使用少量稳定分类和轻量标签，达到条件后再建立主题页 |
| 没有可靠分类就阻断入库 | 标记“暂未归类”，保持可查询，后续再调整 |
| 只在当前分类中回答问题 | 分类只负责导航，复杂问题跨领域查询 |
| 固定创建“理论、实验、概念”等目录 | 根据实际资料动态生成 |
| 一篇资料拆出大量概念页 | 先建简短摘要，综合页按需要创建 |
| 把PDF、TXT和翻译算作三份证据 | 合并逻辑资料组并标明表达层 |
| 把翻译或二次分析称为原始论文 | 分别标注来源类型 |
| 因讲稿引用顶刊就标记为高可信原文 | 可信度跟随当前资料身份，未对照原文不得声称已验证 |
| 普通问答自动写回 Wiki | 默认只读，用户主动要求才写 |
| 搜索结果自动入库 | 先展示或暂存，用户选择后加入 |
