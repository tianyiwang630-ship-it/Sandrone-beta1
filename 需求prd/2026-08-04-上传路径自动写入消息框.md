# 上传路径自动写入消息框

## 背景/原因

当前用户从 Web 对话框的“上传文件”或“上传文件夹”入口完成上传后，文件会直接保存到当前项目工作区，但消息框只显示上传成功提示，不会自动包含新文件的位置。用户还需要手动查找并输入路径，Agent 才能明确知道本轮消息指向哪些材料。

本次迭代希望在上传成功后，把上传对象的项目相对路径自动写入消息框，同时保留用户已经输入的提示词。用户可以连续上传多批文件或文件夹，路径应集中追加在同一个区域内。

## 目标

- 上传成功后，在消息框中显示本次上传对象的项目相对路径。
- 不自动添加“请阅读”“请处理”等任务指令，任务意图仍由用户填写。
- 不覆盖、不改写用户已经输入的提示词。
- 多次上传时复用同一个上传路径区块，并在区块内继续追加。
- 与现有“对齐”开关兼容，避免扩大既有对齐逻辑的改动范围。

## 非目标

- 不改变文件实际上传位置，仍上传到当前项目根目录。
- 不修改 CLI 入口。
- 不修改聊天接口、Agent Runtime、Context / Prompt 组装和模型执行链路。
- 不在本次迭代中把文本路径改造成附件卡片或标签组件。
- 不为文件夹上传增加空文件夹支持；浏览器文件选择目前只能提供其中的文件。
- 不改变现有批量上传的事务和部分失败行为。

## 具体设计

### 1. 消息框中的显示格式

路径使用项目相对路径，并统一使用 `/` 作为分隔符。文件夹路径以 `/` 结尾，便于和单个文件区分。

```text
已上传：
- `论文.pdf`
- `参考资料/`

用户原有提示词
```

路径区块只表达“哪些对象已上传”，不追加任何任务指令。

### 2. 与“对齐”功能的排列关系

未开启“对齐”时，上传路径区块位于消息最前面：

```text
已上传：
- `论文.pdf`

用户原有提示词
```

开启“对齐”时，保留现有对齐提示词位于消息最前面的规则，上传路径区块固定放在对齐提示词之后、用户原文之前：

```text
[现有对齐提示词]

已上传：
- `论文.pdf`

用户原有提示词
```

采用该顺序是为了继续复用现有对齐提示词的开关、识别和移除规则，不让上传功能与对齐功能互相改写内部逻辑。

顺序变化规则：

- 已有上传区块后再开启对齐：对齐提示词插入最前面，上传区块和用户原文保持不变。
- 同时存在对齐提示词和上传区块时关闭对齐：只移除对齐提示词，上传区块成为消息最前面的内容。
- 同时存在二者时继续上传：新路径只追加到上传区块内，不插入对齐提示词，也不追加到用户原文末尾。

### 3. 多次上传与原文保护

第一次上传时创建上传路径区块。后续上传时识别位于固定位置的现有上传路径区块，并把新路径追加到其列表末尾。

例如用户原文为：

```text
翻译成中文，并生成 HTML。
```

第一次上传后：

```text
已上传：
- `论文.pdf`

翻译成中文，并生成 HTML。
```

第二次上传后：

```text
已上传：
- `论文.pdf`
- `参考资料/`

翻译成中文，并生成 HTML。
```

上传路径区块以外的草稿内容必须逐字保留，包括换行、空格和用户自行输入的 Markdown。

### 4. 文件与文件夹路径

- 单个或多个文件上传：使用上传接口返回的最终项目相对路径逐项展示。
- 文件夹上传：只展示本次所选文件夹的根路径，不展开显示文件夹内的每个文件。
- 同一批文件夹内容共同具有的第一层目录名，作为所选文件夹的根路径。
- 同一路径已在上传区块中时不重复添加。
- 用户在重名弹窗选择“保留两份”后，单个文件使用后端返回的实际重命名路径，例如 `论文_(1).pdf`。
- 用户选择“覆盖”后，最终路径与区块中已有路径相同的，只保留一条。

### 5. 上传结果与草稿更新时机

只有上传接口成功返回后，才把对应路径写入草稿。

以下情况不修改消息框：

- 用户没有选择任何文件。
- 用户取消重名处理弹窗。
- 上传请求失败。
- 当前没有选中项目，无法上传。

上传成功后继续沿用现有行为：刷新右侧文件栏、关闭上传菜单并显示成功提示。

### 6. 发送与草稿持久化

- 上传路径区块是普通消息文本的一部分，发送时继续通过现有聊天接口随用户原文一起发送。
- 不在后端或 Prompt 组装层二次注入路径，避免界面可见内容和模型实际收到的内容不一致。
- 发送成功或进入现有排队流程后，本次上传路径随本次草稿一起清除；如果对齐仍开启，只恢复现有对齐提示词。
- 上传路径通过现有草稿持久化机制保存，切换项目或会话后再返回时，消息框内容与离开前一致。

## 架构层定位

本次变化主要位于以下层级：

- **入口层 / Channel Layer**：Web 消息框在上传成功后组织并显示路径区块。
- **Workspace / Memory / State 持久化层**：继续复用现有文件上传接口和工作区落盘能力，不改变其职责。

本次不改变：

- Gateway 控制平面层。
- 消息与会话编排层。
- Context / Prompt 组装层。
- Agent Runtime / Harness 层。
- Agent Loop 执行层。
- Tool / Skill / Plugin 能力层。
- 权限 / 沙箱 / 安全层。

## 实现边界

- 上传公共函数需要把后端已经返回、但当前被前端丢弃的 `FileInfo` 结果交给调用方。
- 上传路径区块的解析、合并和格式化应放在独立前端模块中，避免继续增加 `App.tsx` 的文本处理职责。
- 对话框上传入口使用该模块更新草稿；右侧文件栏上传继续保持现有交互，不自动修改消息框。
- 不新增后端接口，不修改 FastAPI 上传响应结构。

## 异常与边界行为

- 空草稿：只生成上传路径区块。
- 已有单行或多行草稿：上传区块插在规定位置，原文不变。
- 连续多批上传：只存在一个上传路径区块。
- 重复上传同一路径：区块内去重，并保持第一次出现的顺序。
- 文件名或目录名包含中文、空格和括号：按后端返回路径原样显示。
- 用户手动删除整个上传区块后再次上传：重新创建上传区块。
- 用户手动修改区块中的路径后再次上传：保留用户修改后的现有条目，再按最终路径去重追加新条目。
- 用户手动破坏“已上传：”区块的结构后再次上传：将无法识别的内容视为用户原文，并在规定位置创建新的标准上传区块，不删除原内容。

## 验收标准

1. 在空消息框上传一个文件后，消息框显示该文件的相对路径，不出现自动任务指令。
2. 用户已经输入提示词时上传文件，提示词内容和格式不变，上传区块出现在提示词之前。
3. 连续上传多个文件和文件夹时，只产生一个“已上传：”区块，新路径按上传顺序追加。
4. 文件夹只显示根路径，不展开文件列表。
5. 相同路径不会重复显示，“保留两份”产生的不同最终路径能够显示。
6. 开启对齐时，顺序为“对齐提示词 → 上传区块 → 用户原文”；继续上传只更新上传区块。
7. 关闭对齐后，上传区块和用户原文保持不变。
8. 上传取消或失败时，消息框保持不变。
9. 切换会话再返回，未发送草稿中的上传区块仍然存在。
10. 发送消息后，本次上传区块不会自动带入下一条消息。

## 测试要求

- 为上传路径区块的创建、合并、去重和原文保护编写前端单元测试。
- 覆盖开启/关闭对齐前后的组合顺序。
- 覆盖中文、空格、多层路径、重复路径和被用户破坏的区块格式。
- 覆盖上传公共函数返回后端最终路径，确保“保留两份”使用实际落盘名称。
- 不使用浏览器自动化测试。
