# 2026-09-21：增量日志与会话删除清理

## 背景/原因

会话 sess_5b939c9ae7 及两个子 agent 的调试 Log 合计 1,337,010,742 字节。其中 2,622 条 llm_input 每次重复写入完整 messages，合计 1,316,668,461 字节，占 98.48%。用户要求对话、工具调用和结果只记录新增内容，系统提示词变化时记录新版本；删除会话时清理对应 Session、Log 和 Event，避免文件持续积累。

本次只实施日志与删除清理。协作自动回执循环、停止后重新唤醒及一般 Session 保存的 WinError 5 单独处理。

## 具体设计

### 职责和改动层

- Workspace / Memory / State 持久化层：Session 保留当前完整状态快照；Log 记录调试过程；Event 继续支持实时显示和异常恢复。
- Agent Loop 执行层：调用日志改为新增正文和输入变化；工具结果以实际放入 history 的内容为准，同时记录截断信息。被校验拒绝的模型回复保留在 Log，不进入 history。
- Agent Runtime / Harness 层：复用本会话 Log 写入器，重启后从已有日志恢复去重状态；监督进程追加压缩记录后，写入器重新同步。
- 消息与会话编排层：沿用删除前归档、关闭主/子 agent、等待写入结束的流程，补齐残留文件清理和失败后的重试。
- 入口层：沿用现有 FastAPI 删除接口，允许重试清理已归档会话。CLI、Web 和桌面容器共用后端记录机制。

### Log 版本 3

- 日志仍为每个 session 一个 JSONL 文件，不新增数据库或正文目录。
- 正文、思考文本、工具参数、系统提示词和工具定义通过 log_value 记录保存一次；后续以 `$log_ref` 引用。记录中保留角色、消息发生次数、请求编号、工具调用编号、时间和诊断信息。
- 两次用户输入即使文字相同，也保留两次 entry；仅共用正文，不合并两次行为。
- 每次 llm_input 保存相对上次输入的 messages_delta：从哪个位置删除多少条、插入哪些消息。相同前缀和后缀不重复保存，修改、插入、删除、历史压缩及临时恢复指令均可表达。
- 首次 session_started 保存系统提示词和工具定义；内容变化时追加 context_changed。实际调用同时记录所用工具定义引用。旧版本正文保持可查。
- 同一回复在 llm_response、entry 和下一次输入中复用正文；完整输入可以按顺序展开，不能把磁盘中的 messages_delta 当作独立的完整输入。
- 正常流式片段继续实时写 Event，Log 保留完整回复；请求失败、中断或退出时，把已收到的文本合并为 llm_partial_response。进程被强制结束时尚未合并的片段以 Event 为准。
- 工具 Log 保存实际入模结果及原始字符/行数、截断信息，不再额外保存另一份较长的原始工具输出。
- 保留旧 JSONL 的读取支持。出现崩溃尾部残片时，在线读取保留此前完整记录；离线转换采取严格校验，遇到损坏拒绝替换。

### 落盘频率

- 一次用户请求对应的一整次 Agent Loop 运行只提交一次 Log。循环内的多次模型请求、重试和工具调用先缓存在内存中，不逐次写磁盘。
- 正常完成、用户中断和异常失败都由 Runtime 在收尾时统一提交。强制杀死进程时，尚未提交的本轮调试 Log 可能丢失，实时 Event 仍负责页面显示和异常恢复。
- 一次提交使用一次追加写入，不为每条记录单独打开文件。手动上下文压缩等独立运行也在自身结束时提交一次。

### Event

新记录使用紧凑 JSONL，读取器继续兼容旧的多行 JSON。保留已有成功轮次的临时生成片段清理流程，以及未完成请求的消息恢复机制；不删除 Event 消息正文或改变界面协议。

### 会话删除

- 主会话及其子 agent 都先停止、等待受管理写入结束，再清理文件。
- 清理对应 `sessions/<id>.json`、`events/<id>.jsonl`、`logs/<id>.jsonl`、旧版 `*_session_<id>.json` 及各自 `.tmp` 残留。
- 仅匹配准确会话编号，不影响其他会话及用户工作区成果。
- 日志清理失败时保留 Session，使删除接口可重试；不报告虚假的删除成功。
- 已有写入器发现自己的日志被删除后拒绝迟到写入，避免重新创建文件。

### 7 天保留机制

- Log 只保留最近 7 天；Session 和 Event 不纳入这项定期清理。
- 应用启动后由轻量后台线程立即清理一次，之后每 6 小时清理一次。清理只读取目录和文件最后修改时间，不打开或扫描日志正文，因此单个日志大小不会增加检查成本。
- 删除单个文件失败或应用中途退出时，其余文件继续处理；被占用文件留到下一轮重试。清理操作可重复执行，不需要额外数据库、任务队列或恢复文件。

### 旧日志整理及调试读取

使用 `agent-alpha/scripts/compact_realtime_logs.py`。默认在项目 `temp` 中生成整理后的文件；严格比较整理前后所有非流式记录（包括展开后的每次完整输入），校验已有失败片段，并检测源文件是否在整理过程中发生变化。

可使用 `--replace` 原位替换已验证且确实变小的文件；源文件在转换期间发生变化时拒绝替换。启动时只做按修改时间的过期清理，不自动扫描正文或重写历史日志。中间文件留在 temp；成功替换后不再保留等大的原始副本。

同一工具的 `--read` 模式只读展开记录，支持 `--event-type`、`--request-id` 和 `--limit`。复盘 Skill 增加新格式读取说明。

## 验收

- 长对话新增记录不反复写入历史正文；提示词、工具定义变更可以还原。
- 重启、重复输入、中间修改、插入和压缩后的实际模型输入可以逐条重建。
- 正常输出、拒绝的回复、失败片段、工具结果及截断证据保留正确。
- 删除包含活跃子 agent 的会话后，相关记录及临时文件均清理；迟到结果、部分清理失败及重试有覆盖。
- 用本次三个真实大日志验证非流式内容一致性，目标体积降低至少 95%；损坏或并发变化的源日志拒绝替换。
- pytest 中间文件位于 temp；不使用浏览器测试。

## 本次历史处理结果

- 现有 56 个、合计 1,693,454,367 字节的保留日志全部完成逐条校验和原位替换；转换期间没有文件变化或占用失败。
- 转换后合计 29,151,068 字节，减少约 98.28%；最大文件为 `sess_5b939c9ae7.jsonl`，由 725,309,327 字节降为 4,263,619 字节。
- 历史迁移完成后，后续由后台按 7 天保留期持续清理。
