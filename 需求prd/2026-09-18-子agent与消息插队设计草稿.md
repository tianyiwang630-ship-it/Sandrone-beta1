# 子 agent 与消息插队设计草稿

日期：2026-09-18

状态：2026-09-18 已完成本轮实现与验收。下文保留讨论时的设计结论；“仅更新草稿”“尚未实现”等语句描述此前讨论阶段，最终实现与验证范围以第 11、12 节为准。

实施记录：Web 和 CLI 已接入受管理执行进程、协作工具、持久邮箱、运行中引导和结果唤醒，并接入桌面生命周期保护。最终后端回归 357 项、前端 Node 回归 95 项及生产构建通过。验收证据和边界见第 12 节。

## 1. 背景／原因

主要服务两类需求：执行明确要求使用子 agent 的 skill；使用独立上下文完成验证。子 agent 同时需要能实际编辑文件、运行脚本、承担任务，不能被设计为只有阅读权限的检查器。并行提速是附带收益，不是唯一目的。

另一个本次需求是运行中消息插队：用户对主 agent 的直接引导、主副 agent 的消息、子 agent 之间的交流，应复用公共消息投递机制，不等待整个 Agent Loop 完成。

总体取向：Harness 尽量薄，把任务判断、分工、方向调整和协作交给主 agent。后端负责身份、执行生命周期、持久化、消息投递和既有权限规则。

## 2. 已确认的定位与边界

- 主 agent 通过工具创建和使用子 agent。工具背后是有独立上下文、完整执行循环和工具能力的 agent。
- 子 agent 能读取、编辑、写入文件、运行脚本；验证是任务用途，不是默认只读的特殊运行时。
- 子 agent 不得再创建子 agent，实际不向它暴露创建能力。
- 每个主会话最多同时运行 10 个子 agent。完成后保留的实例数量不应直接等同于正在运行数量；等待、恢复等状态如何占用名额仍需在计划中明确。
- 只有用户明确要求，或适用的项目指令／skill 明确要求，才创建子 agent。这个约束写入工具描述和提示词，不增加自然语言关键词拦截，不让模型仅以提效为由自行启动。
- 主 agent 决定如何分派、补充消息、调整方向、停止或重新安排子任务；后端不自动识别用户是否改变了任务方向。
- 主任务由主 agent 对用户统一交付。需要用户补充信息时，由主 agent 统一询问；既有权限授权不因委托而扩大。
- 允许子 agent 之间直接交流。本轮不额外增加通信次数限制、累计对话预算、循环检测、内容审查或单独的防互相回复机制。相互通信可能反复唤醒的风险已讨论，用户选择先开放。

## 3. 工作目录、文件与环境

### 3.1 共享工作目录

子 agent 默认使用主 agent 的工作目录，直接访问同一批项目文件。后端不为每个子 agent 创建专属工作目录、临时目录、项目副本或 Git worktree。

agent 可以根据任务自行创建临时文件夹和脚本，遵循所在项目约定。提示词交代可修改内容、避免修改的内容和任务分工。

### 3.2 接受文件协作冲突

不新增文件锁或自动合并机制。通过提示词提醒避免同时修改同一文件，编辑前读取最新内容，不覆盖或回退他人改动。

允许共享编辑失败，但一次文件操作错误应作为工具结果交回当前 agent，让它重新读取、调整并继续；不能导致整个 agent 循环或其他子任务直接退出。

这种恢复不能自动发现所有静默覆盖，第一版不承诺并发编辑不会丢失内容。用户停止、既有轮数限制等正常终止条件仍然有效。

### 3.3 能力与环境默认方向

复用现有 AgentRuntime、AgentLoop、工具和 skill 加载机制，独立维护历史与上下文。默认沿用主 agent 模型及可用能力、去掉递归创建能力，是当前讨论的默认方案；本轮没有新增模型、角色或工具集覆盖参数。

创建时固定不继承主 agent 的对话历史，只通过任务说明交接，不提供历史继承范围参数。身份、工具说明及适用的项目规则仍由运行时提供；不继承历史不等于取消必要规则。

不为每个子 agent 安装独立 Python 环境。环境变量、终端、MCP、浏览器等有状态资源的实际共享行为需实施前检查，不能把独立上下文误称为操作系统级隔离。

## 4. 身份、持久化与恢复

- 后端分配稳定身份，记录 agent ID、会话身份、父子关系，并避免混淆 agent 实例、一次执行和一条消息。
- 保存恢复所需历史消息、实际模型上下文／压缩结果、工作目录、必要运行配置、运行状态及消息记录。
- 优先复用现有主会话存储、日志和恢复链路，不另造一套完整存储系统。需核实哪些字段已经保存、哪些需要补齐，不能只凭日志存在就认为能完整恢复。
- 停止结束当前执行，不销毁 agent。保留 ID、上下文与记录，之后能凭 ID 追加输入并继续。
- 程序重启后不自动执行旧任务，但应能按原 ID 重建子 agent，并在明确调用后继续；先前运行状态不能无条件当成仍在运行。
- 不自动回滚已修改文件。第一版不单独增加含义重叠的暂停、删除工具操作。
- 固定身份说明由后端组装，不依赖容易被压缩掉的历史：自己的 ID、所属会话、上级身份和协作笔记路径。

### 4.1 Agent、任务、消息与一次运行

- Agent 是有稳定 ID、上下文和历史的执行者。
- 任务是交给它做的事情，可以通过创建时或后续的消息交代。
- 消息是交流输入，可以表达提问、补充要求、复查或下一项工作；后端不根据正文强制划分聊天与新任务。
- 一次运行是收到输入后执行到回复、等待或停止的过程，不等于 agent 的完整生命周期。

第一版不单独增加一套 task 分派接口或完整任务管理系统。与原工作衔接紧密的修改、复查使用原 ID 继续；完全不同的工作或需要独立重新判断时可以新建 agent。

### 4.2 完成、空闲和资源释放

子 agent 完成本轮后进入空闲，保留 ID、上下文和结果，不自动删除。空闲实例不占同时运行 10 个的名额；后台等待等其他状态的名额计算仍需细化。

后端可以按需释放空闲实例的内存和连接，再凭持久化记录重建。资源释放不是删除历史，也不表示原 ID 失效。具体释放策略尚未确定，不默认引入复杂缓存或淘汰算法。

主 agent 每次回答结束或用户点击主聊天中断，不意味着其子 agent 一起结束。普通中断只针对主 agent 当前执行；关闭整个应用才统一停止全部受管理的后台执行。用户也可以要求主 agent 用工具停止指定或全部子 agent。第一版不向主 agent 提供永久删除子 agent 的操作。

### 4.3 用户中断、主动停止子 agent 与关闭应用

本节替代早期“主聊天中断会连带停止全部子 agent，且阻止结果唤醒主 agent”的方案。

| 情况 | 处理范围与后续行为 |
|---|---|
| 用户点击主聊天中断 | 停止主 agent 当前执行，不停止子 agent；子 agent 的消息或结果仍允许唤醒主 agent |
| 用户要求停止某个或全部子 agent | 主 agent 按 ID 调用 `stop`，停止目标当前执行，保留记录；无需用户逐个操作 |
| 用户再次给主 agent 发消息 | 在原会话开始新一轮，不自动恢复全部已停止的子 agent |
| 给已停止的子 agent 发新任务消息 | 按原 ID 和历史开始新一轮，无需额外 `resume` 操作；不是从旧工具的程序断点继续 |
| 正常退出 Agent Alpha | 统一停止主 agent、子 agent、工具脚本及应用管理的进程树，保留持久化记录与已有产物 |
| 强制结束应用、崩溃或电脑关机 | 执行被中断；进程生命周期需要系统级兜底，重启后不得将旧“运行中”记录当成仍在执行 |

关闭 Agent Alpha 必须停止它管理的全部后台进程，不能仅关闭窗口或留下子任务继续执行。范围是 Alpha 启动和管理的执行资源，不包括用户原本独立运行的程序。正常退出使用统一清理；强制退出需要操作系统级的进程归属／生命周期机制兜底，具体实现方式在计划中核实，不能只依赖进程退出前的清理回调。窗口、后端和进程树的实际退出链路必须验证。

单独的“强制停止子 agent／停止全部子 agent”界面入口留作后续能力，不作为本轮已经确认要实现的新增按钮。当前通过主 agent 工具停止。

### 4.4 中断收尾与再次执行的基础要求

静态审计发现：现有循环中断时可直接停止等待后台工具线程，下一轮又会清除同一个中断信号。因此旧工具未退出时，新任务可能开始，甚至让旧工具错过停止信号。不能直接把现有中断实现当成可靠的停止／恢复基础。

后续实现需解决以下问题，具体机制在实施计划中细化：

- 运行级取消信号独立，旧运行取消后不因下一轮开始被清除；旧工具始终使用所属运行的信号。
- 区分“正在停止”与“已停止”，确认目标运行的工具已退出或完成收尾，不能仅凭循环返回就宣称停止成功。
- 同一个 agent 的旧执行尚未收尾时，新消息先保存；收尾后再执行，避免新旧工具重叠。该等待不阻止其他仍在正常工作的子 agent。
- 本地命令取消应终止所管理的进程并确认退出；不能只依赖工具主动响应取消，应按第 4.6 节在短暂收尾后强制终止本地执行。确认失败时如实报告，不能用超时假装已停。Python 线程不能通过结束等待来等价终止。
- 收尾确认需覆盖工具启动的后台异步操作和受管理进程，不能仅以工具函数返回或外层线程退出为依据。当前 `mcp_manager.py` 的 `_run_coro()` 把协程交给后台事件循环，再调用 `future.result(timeout=...)`；等待超时不等于后台操作被取消，必须纳入统一终止链路。
- 已完成的文件修改不自动回滚；外部操作取消后结果不确定时保留事实，不声称远端副作用已经撤销。旧运行迟到结果不能混入新运行。

这些要求不改变普通中断的范围：停止主 agent 的当前操作，不连带停止其他子 agent，也不禁止其后续消息唤醒已完成收尾的主 agent。

### 4.5 重启后只补充事实上下文

只对曾创建过子 agent 的主会话添加重启说明。普通没有子 agent 的会话不增加本项特殊提示或处理流程。

识别依据是后端持久化的父子关系：创建子 agent 时记录所属主会话；恢复主会话时检查是否存在关联子 agent。无需模型判断，不依赖 AI 维护的 Markdown 笔记，也不要求当前必须有正在运行的子任务。

应用重启后，该主会话第一次执行时，后端自动加入简短事实说明，例如：

> 应用已重新启动。此会话曾创建子 agent；上次退出前尚未完成的执行可能已中断，未自动恢复。

不添加“请检查”“请恢复”“下一步应如何做”等行动指令，不替主 agent 制定恢复计划。主 agent 根据用户消息和这个事实自行决定是否查看笔记、查询状态或联系子 agent。用户不需要知道重启前有哪些子任务，更不需要手动交代中断事实。

后端记录本次应用启动的说明是否已送入该会话，避免每条消息重复添加；下一次重启可再次说明。说明随上下文正常持久化，不能只在界面显示而模型看不到。

重启本身不自动启动子任务。历史中已完成的结果保留；此前未完成的执行不能继续显示成真实运行中。恢复状态的具体表示及异常退出判定需在计划中落实；不能断言具体是断电或崩溃，原因不明时只说明重启和可能中断的事实。

### 4.6 快速强制终止的实现方案（已确认方向，尚未实现）

采用“独立执行进程＋Windows Job Object 管理＋管理后端持续保存记录”的路线。不能只增加停止信号、线程等待或 `future.cancel()`，也不能把无限处于“正在停止”作为正常处理方案。这是运行时执行边界的调整，不是单个工具的小修补。

#### 4.6.1 管理后端与执行进程分离

管理后端负责会话记录、消息投递、启动、停止和执行状态；每个正在运行的 agent（包括主 agent）在可单独终止的工作进程中执行。管理后端不能依赖工作进程中的模型或工具响应，才能完成停止。

```text
管理后端
  ├─ 主 agent 执行进程及其工具子进程
  ├─ 子 agent A12 执行进程及其工具子进程
  └─ 子 agent A13 执行进程及其工具子进程
```

主副关系是消息和任务关系，不应把所有子 agent 的执行进程归入主 agent 的单独终止范围。停止 A12 只结束 A12 的执行资源，停止主 agent 也不因此结束 A12、A13。

仍复用现有 AgentRuntime、AgentLoop 和工具实现，并共享同一项目工作目录；进程隔离不要求新增每个 agent 的工作目录或 Python 环境。具体进程启动协议、进程间消息通道及空闲复用方式在实施计划中细化。

#### 4.6.2 Windows 进程归属和强杀

为每个 agent 的执行资源建立独立 Job Object，由管理后端持有控制句柄；工作进程及其普通子进程纳入对应 Job。强制停止使用 `TerminateJobObject` 结束该组本地进程，不仅杀最外层命令。

- 工作进程在允许执行任务前必须已纳入 Job，例如挂起创建、完成归属后再恢复执行，避免先运行后登记的时间窗口。
- 禁止无意继承控制句柄或允许进程脱离 Job，避免管理方退出后句柄仍存活、后台不能被清理。
- 不能仅依靠事后枚举 PID 或一次 `taskkill /T /F` 作为完整保证；通过服务、其他进程代理启动的操作等不自动归组的路径必须检查。
- 按执行 ID 关联进程和结果，确认旧组退出后才允许该 agent 再次执行。旧进程迟到事件不能覆盖新运行状态。
- Windows Job 的嵌套、宿主环境已有 Job 限制和实际子进程继承行为需验证；无法建立所需归属时必须明确报错，不能静默退回无法强停的线程方案。

Windows 提供 Job 内进程统一终止，以及最后一个 Job 句柄关闭时结束进程的 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 机制。官方依据：[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[Nested Jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs)。该机制覆盖受管理本地进程，不表示可以终止任意外部服务。

#### 4.6.3 停止时序与时延

1. 用户中断或主 agent 调用 `stop` 后，管理后端立即标记目标正在停止，禁止其启动新动作，发出本轮取消信号。
2. 只给予很短的正常收尾时间；讨论中的候选是 300～500 毫秒，不是已承诺或已验证的最终时限。
3. 到期仍未结束，直接强制终止目标 Job，不再等待模型、工具超时或执行进程的同意，也不新增用户确认。
4. 核实本地进程已退出，保存中断状态；同一 agent 的待处理新消息才可启动新的执行进程。

整体停止有明确总时限和失败反馈，不无限等待正常清理。具体宽限时间、确认退出的时限和验收指标由后续实现测试确定，不承诺操作系统在一切故障下零延迟退出。若系统终止失败，不能显示已停止或并发恢复旧 agent；应明确报告失败状态。

#### 4.6.4 MCP 后台操作及外部副作用

agent 的本地 MCP 客户端、后台事件循环和不可取消的工具执行必须处于可终止的执行边界内。正常取消时追踪并取消对应异步任务；无法结束时以终止工作进程兜底。本地 MCP 服务也必须有明确归属并纳入进程管理，不能只结束等待其结果的线程。

不能为了停止一个 agent，无条件杀掉其他 agent 共用的 MCP 服务。若连接或服务共享，需验证按请求取消能力；不满足独立强停要求时，调整为可单独终止的执行资源。具体服务共享策略在实施计划中逐项核实。

远程 MCP、网络服务已经接收的请求不能通过本地强杀撤销。取消后可能已产生的远端修改需保留结果不确定事实；本地停止完成不等于远端业务回滚，恢复不能盲目重复提交。

#### 4.6.5 应用整体退出兜底

应用级生命周期管理覆盖自有后端及所有 agent 执行组；使用 Job 的关闭即终止机制和明确的句柄所有权，使窗口主进程被强制结束时也不只依赖 `before-quit` 清理回调。管理后端异常退出同样应触发其工作进程组清理。具体应用级 Job 的持有者、嵌套层级与启动方式需在计划中落到实际调用链，不能让已死亡的进程承担后续清理责任。

正常退出采用短暂、并行、有总时限的清理流程，到期终止全部自有执行资源。应用进入退出状态后禁止启动新执行或因子任务消息唤醒任务。

当前 `frontend/desktop/backend.cjs` 会先等待浏览器清理（最长 30 秒），再对自有后端调用 `kill()`；该串行链路不能作为快速退出的最终方案。浏览器清理不能长时间阻塞应用退出，超时强制清理应由应用级资源管理兜底。

桌面正式运行模式需要明确拥有自己的后端，不能静默复用一个不受其生命周期管理的既有后端，同时承诺关闭窗口即可结束全部工作。现有连接已启动后端的行为需调整并区分开发使用方式，不误杀用户独立运行的服务或其他应用。

#### 4.6.6 共享浏览器是必须验证的边界

当前 Browser Harness 使用共享通道。结束某个 agent 的客户端进程，不保证已经发到浏览器或 daemon 的动作停止。

实施前验证共享通道是否支持取消对应请求并确认结束；若不能，需要给要求独立强停的执行分配可单独终止的浏览器执行资源，或先调整通道归属。不能一方面继续复用不可取消的共享通道，一方面承诺单独停止 A12 的全部动作且完全不影响其他 agent。

这里尚未确定独立浏览器实例／profile 等具体实现，不把它自动扩展为每个 agent 都必须创建工作目录。用户原本独立运行的浏览器不属于可随意强杀的目标；Alpha 自有浏览器和 daemon 必须受应用级退出管理。

#### 4.6.7 持久化与恢复

管理后端持续接收并保存执行事件和上下文检查点，不等工作进程停止时才集中保存。执行进程被强杀后保留 agent ID 和最后已持久化的历史，管理后端记录中断或结果未确认状态。

强杀时尚未送达／保存的内存内容不承诺完整保留；工具副作用与日志保存之间可能存在间隙，不能据此承诺恰好执行一次。下一次按原 ID 重建执行进程，而不是恢复旧 Python 线程；通过已有记录和实际产物继续判断进度。

## 5. 项目内协作笔记

协作 Markdown 是 AI 的记忆辅助，不是后端权威状态表。

约定位置的当前方案：`<用户项目工作目录>/temp/subagent-notes-<主会话短ID>.md`。不放 Windows 用户主目录，不要求用户去 Alpha 内部运行目录查找笔记。

- 不修改用户的 `AGENTS.md`，不使用容易混淆的 `agents.md` 文件名。
- 主 agent 可在首次分派后创建，记录子任务 ID、分工、结果和待办；子 agent 也可以编辑，不加专门只读限制。
- 后端不持续生成或同步 Markdown 状态表。AI 自行维护，遵循共享编辑提醒。
- 后端仍保存工具运行所需的真实身份和状态；改笔记不会修改实际收件人或运行状态。
- 提供无需事先知道子 agent ID 的列表查询能力，压缩或笔记丢失时仍能找回基本任务记录。
- 稳定身份提示中明确给出协作笔记的路径，通信工具描述也提示忘记 ID 时查看该文件，必要时调用 `list`。路径提示不能只保存在会被压缩的历史里。
- 清理 temp 可能丢失手写备注，但不应删除后端持久化的 agent 身份和历史。

## 6. 工具交互的当前轮廓

主 agent 使用工具创建、发消息、改名、查看／列出、等待和停止子任务。当前倾向一个 `subagent` 工具用操作参数区分；下文所列参数语义已确认，最终工具名称、完整 schema 和返回结构仍待实施计划细化。

子 agent 使用不同名称的通信工具。最初提议 `parent_message`；因已允许子 agent 相互通信，最终命名不能暗示仅能联系上级。发送目标统一使用 `target_id`，不向子 agent 暴露创建能力。

### 6.1 创建和最终成果

创建时任务交接只要求两个字段：

- `task_name`：简短任务名称，方便理解分工，可以重名，不作为通信寻址标识。
- `message`：完整任务交接说明，包含目标、必要背景、相关文件、注意事项和期望结果。工具描述提醒交接清楚，不强制拆成多个字段。

后端生成并返回唯一 agent ID。第一版固定不继承主 agent 历史，不提供 `fork_turns` 或同类参数。

创建立即返回已启动及子 agent 身份，不阻塞到任务完成。最终成果包含实际文件修改和给主 agent 的文字反馈；共享工作目录不需要自动搬运成果文件。

完成后保留上下文，可以继续追问、安排复查或追加任务。验证不设置强制交付关卡，不限制验证 agent 必须只读。

### 6.2 发消息与异步回应

从子 agent 视角看，主 agent 的输入像用户输入，应处理并回应。不要求调用者区分“只送消息”和“要求继续执行”。

通信参数只保留 `target_id` 和 `message`。主副 agent、子 agent 之间统一按 ID 寻址，不支持用任务名称、别名或路径替代 ID。发送者身份、消息 ID 和时间由后端记录，不让模型填写。

不要求填写“问题、回复、进展”等消息类型参数。内容含义由接收方理解；任务完成和执行失败由运行时产生状态事件。`list` 返回 ID、名称和状态，配合协作笔记找回目标。

发消息的工具立即返回已接收，真实答复稍后送回。主 agent 可继续做其他工作或主动等待。已接收不等于已处理或已完成。

异步答复应能关联原发送操作；本轮未增加模型必填的回复关联参数，内部关联和结果交付结构仍需在实施计划中细化。不得把后来答复伪装为对既有工具返回的原地修改。

子 agent 可以工作中提问。有其他独立工作时可继续，必须得到答案才能推进时可等待。等待由运行时管理，不让模型反复轮询。

### 6.3 结束与唤醒

- 主 agent 正在运行：问题和结果进入当前循环。
- 主 agent 正在等待子任务：问题也必须能唤醒它，避免主等子完成、子等主回答的互相等待。
- 主 agent 本轮已结束：子任务的问题、完成或失败可以触发主 agent 下一轮，接回已有委托结果。
- 普通运行进度展示不要求单独唤醒主 agent。agent 主动调用通信工具发送的文字按正常输入处理，不要求后端根据正文猜测类型或过滤“谢谢”等消息。
- 用户点击主聊天中断：只停止主 agent 当前执行，子 agent 继续工作；其消息或结果仍可唤醒主 agent。关闭整个应用时全部受管理执行停止，重启不自动恢复子任务，详见第 4.3—4.5 节。
- 区分本轮回答结束、某个子任务结束、整个任务完成。必要子任务尚未收尾时，不应误报整体完成。

### 6.4 等待工具与默认用户体验

`wait` 是按需使用的工具，不是创建或发消息后的必经步骤。

- 接收一组 agent ID，以及可选的等待时长；参数的最终拼写、默认时长和最大时长尚未确定。
- 任意目标出现可交付的新消息、完成或失败，就先返回，不要求全部完成。无需后端识别自然语言问题类型。
- 超时仅返回当前状态，不停止子任务，也不把超时当成任务失败。
- 主 agent 可以处理已有结果后继续等待剩余任务，不通过连续短时间调用制造忙轮询。
- 等待应能被用户直接引导等新输入唤醒，与公共消息插队机制保持一致。

默认交互方式是“说明进度＋后台运行＋结果唤醒”：当前没有其他必要工作时，主 agent 告诉用户已经分派什么、目前进度及结果回来后会继续处理，然后结束本轮执行。子任务继续运行，问题或结果到达后再唤醒主 agent。

界面应区分“主 agent 正在处理”和“等待子任务”。主 agent 已结束本轮后，不应继续以持续思考转圈或长时间挂着工具调用的形式制造仍在主动工作的假象；可以显示子任务运行状态。

当下一步需要立即接回子任务结果时，可使用 `wait`。例如目标模式或 skill 要求独立验证，必须获得验证结果后才能继续交付；等待较久时也可以先说明进度并结束本轮，由结果到达后唤醒。是否使用连续挂起的 `wait` 不影响“未验证完成不能声称通过”的要求，也不表示本次新增强制验证关卡或目标模式本身。

无论通过 `wait` 还是后台唤醒接收结果，均进入同一套结果处理流程，避免重复交付。

### 6.5 改名与操作清单

允许主 agent 修改子 agent 的显示名称。改名不改变 ID、上下文、历史或任务要求，也不自动启动执行。任务方向改变仍通过 `message` 交代；名称需要同步时，再调用 `rename`。

| 操作 | 已确认的参数语义 | 行为 |
|---|---|---|
| `create` | `task_name`、`message` | 新建并交接任务，返回唯一 ID |
| `message` | `target_id`、`message` | 提问、补充要求或安排后续工作，异步回应 |
| `rename` | `target_id`、`task_name` | 仅修改显示名称 |
| `list` | 默认无需 ID，可按状态筛选或查询更早记录 | 列出当前主会话的子 agent |
| `status` | `target_id` | 查询指定 agent 的状态 |
| `wait` | 一组 ID、可选等待时长 | 等待新消息或结果，超时不停止任务 |
| `stop` | `target_id` | 停止当前执行，保留身份和历史 |

不提供永久删除操作。子 agent 的通信能力不等于拥有主 agent 的全部管理操作，尤其不能创建下属。

### 6.6 数量增长后的列表与历史查询

`list` 默认限定当前主会话，不混入同一项目中其他主会话的子 agent。

- 默认最多返回 10 条：正在运行、等待答复的优先，其余按最近交互时间排序。
- 支持按状态筛选，例如 `status="running"` 查询正在运行的子 agent。完整状态枚举后续细化。
- 支持翻页查询更早记录；具体分页参数尚未确定。
- 已知 ID 时可直接发送消息或使用 `status` 查询，不受前十条限制。
- 创建、发送消息、收到答复、停止或改名更新最近交互时间；单纯查看列表和后台日志不刷新排序时间。
- 后端使用持久化记录中的状态和时间字段筛选排序，不要求为此专门引入链表。

列表显示 10 条与最多同时运行 10 个是两个独立概念。掉出列表前十条不代表 agent 被删除、失效或不能联系。

协作笔记由 AI 维护，帮助回忆分工、原因和待办；后端列表负责准确的 ID 与状态。找旧 agent 可先查笔记，也能翻页查询持久化记录，避免笔记漏记或被清理后无法找回 ID。后端不因新增列表功能而接管 Markdown 笔记。

## 7. 统一的消息插队／直接引导

用户已确认：参考本地 Codex 的运行中引导设计，不再自创额外执行规则。

- 用户聊天增加“直接引导”，保留原有任务结束后处理的排队方式。
- 主 agent 向子 agent 发消息、子 agent 向主 agent 发消息，复用同一运行中投递机制；子 agent 互相通信也纳入公共机制。
- 插队不能等待整个 Agent Loop 结束；应在执行期间合适的输入接收边界进入当前任务。
- 同一个 agent 同时只有一个执行循环，不因收到消息并发启动第二个循环。
- 空闲时按前述回应／唤醒约定处理。普通主聊天中断后，子 agent 消息仍允许唤醒主 agent；同一 agent 的旧执行需先完成中断收尾。应用退出期间不启动新执行，重启不自动恢复子任务。
- 保留来源身份，子 agent 的结果不冒充用户指令。
- 实施时继续追踪 Codex 对模型请求、工具执行、待处理输入、轮次收尾和竞态的实现，明确移植边界。
- 先前讨论过的“收到消息后跳过一批尚未执行工具调用”等具体机制没有确定，不可直接按已确认需求实施。

统一消息插队机制不代表照搬 Codex 的所有工具语义：本地 Codex V2 区分不启动新轮次的 `send_message` 和空闲时触发执行的 `followup_task`；本项目已选择不向调用者强制暴露这一组区分。

### 7.1 用户与子 agent 同时发来消息

当主 agent 结束本轮、子 agent 仍在后台运行时，用户的新问题与子 agent 的消息可能同时到达。两者进入同一消息接入流程：

1. 分别保存消息，保留来源及可追踪的到达顺序，不互相覆盖。
2. 主 agent 空闲时只启动一个执行循环；已运行时复用当前循环，不按发送者再创建一个并行循环。
3. 赶上同一次模型调用的消息可以一起交付；晚到的消息通过插队机制在后续输入边界交付，不修改已发出的模型请求。
4. 收尾时协调新消息到达与运行结束，避免遗漏消息或重复启动循环。

提示词要求优先回应用户当前问题，将子 agent 反馈作为协作信息处理；相关内容可结合回答，无关内容可以分别说明。这个优先原则不要求后端做语义分类，也不能把子 agent 信息伪装成用户指令。

## 9. 第二轮五个问题的确认结论

| 问题 | 确认结论 |
|---|---|
| 是否继承主 agent 历史 | 固定不继承，只通过任务说明交接，无历史继承参数 |
| 创建时如何表达任务 | `task_name`＋`message`，不强制拆分背景、验收等字段 |
| 如何找到通信对象 | 只按后端生成的 ID；提示中给出协作笔记路径，必要时 `list` 查询 |
| 是否填写消息类型 | 不填写；通信只传 `target_id`＋`message`，身份等由后端记录 |
| 等待多个子任务的行为 | 新消息或任意任务完成／失败就返回，超时不停止任务；默认优先说明进度后后台运行，由结果唤醒 |

后续场景讨论新增确认：用户与子 agent 消息共用一个循环；完成后空闲保留、资源可释放但不删除记录；任务通过消息交代，名称可独立修改；列表限当前主会话、活跃优先、默认 10 条并可翻页查询历史；本项目占位工具不作为设计依据。

中断／退出讨论新增确认：普通主聊天中断不停止子 agent，其消息可唤醒主 agent；通过工具停止指定子 agent；关闭应用必须结束全部受管理进程；重启后不自动恢复子任务，仅在使用过子 agent 的主会话中一次性补充重启事实，不附加行动指令。早期“主聊天中断一律停全部、迟到结果不能唤醒”的规则已撤换。

Codex 参考证据范围：本地仓库已核对 TUI 的指定会话中断、`turn/interrupt` 请求和核心中断处理，普通路径未遍历停止所有子 agent；TUI 另有按任务 ID 停止的入口。没有核实当前 Codex 桌面按钮的前端完整行为，不将 TUI 入口描述为桌面上必然存在的按钮。本项目的整体应用退出及重启事实提示是已讨论的项目需求，不声称与 Codex 桌面完全相同。

强制终止实现方向已确认：管理后端与 agent 执行进程分离，通过 Windows Job Object 对目标执行资源强制终止，应用级生命周期管理兜底退出，管理后端持续保存记录。详见第 4.6 节；不再仅依赖线程取消或无限等待工具收尾。

## 11. 实施记录与剩余验收（2026-09-18）

### 11.1 已接入的具体机制

- Runtime / Harness：Web 后端用 `ProcessRuntime` 管理独立工作进程，工具和模型在进程内执行。启动门闩在 Job 归属完成后才打开。普通运行结束可保留该实例；中断后确认进程组清空再重建。同一次实例不允许两个调用并行。
- 停止：每轮独立取消信号；正常中断先发取消，400 毫秒后仍未结束则强杀，进程组退出确认时限 2 秒。状态区分 running、stopping、stop_failed。失败不伪装成停止成功。快照缺失工具结果时记为结果未知。
- 持久化：工作进程每次追加历史都向控制进程提交快照，收到保存确认才继续；MCP 超时取消其后台 future，强杀仍由进程边界兜底。
- 编排：沿用 SessionStore，在会话 metadata 中持久化父子关系、运行配置、邮箱及交互时间。消息保留 ID、发送者、回复关联和投递状态；运行边界取新输入，快照确认消费；收尾检查未消费的新输入并启动下一轮。
- 工具：主 agent 为 `subagent_create/message/rename/list/status/wait/stop`；子 agent 只有 `agent_message/list/status/wait`，服务端也校验管理权限及同一主会话范围。创建固定不继承历史。
- 名额：运行、等待输入或权限、正在停止及停止失败都占当前执行名额。空闲不占；已有子 agent 在满额时收到消息先持久排队，释放名额后启动。创建第十一个正在执行的子 agent 返回错误。
- 列表：默认十条，活跃优先，offset 翻页，可按 status 筛选。笔记仍由 AI 自行维护，后端仅提供路径，不创建文件。
- 等待：`target_ids` 加可选 `timeout_seconds`，默认 30 秒、范围 0—60 秒。消息/结果或用户引导可提前返回；超时不取消。消息通过正常输入消费，wait 返回状态以避免正文重复投递。
- 入口：Web 保留排队发送并增加“直接引导”；显示后台子任务状态，轮询发现自动唤醒的主会话；子任务权限请求在主会话展示。
- CLI：已接入同一 AgentManager 和受管理工作进程，支持后台协作消息、权限处理、`/steer` 引导及 `/stop` 主会话停止；恢复会话保留原 ID，退出时清理受管理执行。
- 收尾：结果返回后，直到邮箱收尾完成仍占用该 agent 的执行位置；此时到达的新消息先保存，再接续下一轮。手动压缩也走邮箱收尾，压缩成功或失败都不会搁置期间收到的消息；压缩操作不冒充子任务答复。
- 停止与退出：工具停止某个子 agent 时，暂停该目标的新执行接入，期间的新消息持久保存，关闭旧执行后再调度，避免旧停止操作误伤下一轮。清理失败保留实例引用供再次清理；应用进入关闭状态后，构造中的实例不能再登记成可执行实例。
- 删除／归档主会话：先关闭该会话及关联子 agent 的消息入口，再并行停止执行，并等待监督线程完成日志和快照收尾；删除文件在收尾之后进行。停止确认失败则保留记录，不把未退出的执行当成已删除。归档的任务不再自动投递结果或被调度。
- 迟到工具请求：创建、发消息、改名、等待和停止在后端接入时核对调用者的运行 ID 仍有效，旧执行停止后不能借延迟请求继续修改协作状态。
- 取消通道：强杀计时独立于 IPC 发送；控制通道繁忙时，取消消息可以稍后送达，但不能拖延进程组强制终止。
- 前端引导：发送中的直接引导禁止重复点击；成功回执只清理原会话未被改动的草稿，不覆盖发送期间新输入的内容。自动唤醒的状态跟踪不抢占已有发送流程。
- CLI 上下文导出：执行检查点同时保存系统提示词、工具数量和角色信息；释放工作进程后仍可导出最后持久化的提示词与压缩历史。
- 监督线程：每次执行使用独立监督线程，避免固定线程池被等待子任务的主会话占满；模型与工具仍在受管理进程中运行。
- 桌面退出：`desktop_host` 将应用级 Job 的唯一控制句柄交给 Electron；启动器另持后端 Job。Electron 或启动器被强制结束都能触发系统清理。桌面关闭给后端最多 1 秒收尾机会，然后终止自有启动器；桌面不再复用独立启动的后端。
- 浏览器：受管理工作进程按稳定 agent ID 使用各自浏览器 profile 和 daemon 通道，避免共享不可取消通道。这些是运行资源目录，不是 agent 的项目工作目录；项目文件仍共享。浏览器和 daemon 的普通子进程继承执行 Job。
- 重启：不自动重跑；根据持久父子关系，仅在曾创建子 agent 的主会话下一次执行时补一次事实说明。
