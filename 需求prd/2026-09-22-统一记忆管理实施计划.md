# 2026-09-22 统一记忆管理：产品设计与实施计划

状态：首版已实施（2026-09-22）。本文保留产品规则和实现边界，实际接入与验证见第 10 节。

依据：`../自进化记忆草稿.md`（2026-09-22 更新）。产品行为以草稿和本文已确认边界为准；本文中的模块、接口、数据结构是实施方案，可按代码核查适当收敛，但不能改变产品含义。

## 1. 背景、目标与范围

现有草稿定义了整理 Agent、审核 Agent 和受限记忆写入，但用户缺少统一的查看、修改、恢复和调度控制入口。本轮补全交互，并将产品动作对应到现有 Harness 链路。

“记忆”统一包含用户信息 `user.md`、长期经验 `memory.md`、技能 `references` 经验。它们共用用户页中的“记忆管理”入口、一套整理审核流程、一套自动处理进度；不建立互相独立的记忆整理和技能整理系统。

首版交付：

- 全局两份记忆文档的查看、手动编辑、字符限制、最近八版查看与恢复。
- 三个独立开关：启用两份文档、自动更新两份文档、自动更新技能经验，默认均开启。
- 自动与手动各一份持久补充提示词，每份同时用于记忆与技能，不按对象拆分。
- 选择历史开始、结束时间，手动启动一次整理；自动按时间和轮次门槛运行。
- 整理、审核两个受限角色，日志分段读取、历史版本读取、本批临时笔记、可恢复任务及后端写入校验。
- 新建日常 Agent 实例时在系统提示词中加载记忆；不刷新运行中实例，不修改对话或工具 history。

不增加：记忆即时触发口令、候选记忆数据库、长版记忆、第三个审核者、技能主文件自动改写、运行时记忆刷新、独立技能整理入口、用户逐条审批提案、正常完成弹窗。首版不增加技能历史版本编辑器；八版恢复只适用于两份 MD。

## 2. 已确认的产品规则

### 2.1 页面结构

保留现有“用户”导航，在账号和本地权限下添加可展开的记忆管理组件，明确“所有项目共用”。

| 页面区域 | 操作与反馈 |
| --- | --- |
| 用户与长期记忆 | “启用记忆”“自动更新”；两份 MD 标签；内容、字符数、编辑、保存、取消、历史版本、恢复 |
| 技能经验 | “自动更新”；说明只更新允许的 references，不修改 SKILL.md，也不控制技能本身是否可用 |
| 补充要求 | 自动、手动两份独立配置，均可编辑、保存、清空，保留到用户下次修改 |
| 现在更新 | 开始时间、结束时间（默认现在）、本次允许更新对象；启动后显示阶段和结果 |
| 状态与帮助 | 最近整理时间、整理中/审核中/完成/无需修改/失败；简短名称配可悬停或点击的说明 |

固定展示生效说明：“记忆更新及启用状态的变更，在新对话中生效；当前对话不会实时更新。应用重启后恢复对话时，也会加载最新配置和记忆。”不承诺每条新消息刷新，也不为了开关重建运行实例。

### 2.2 开关矩阵

| 动作 | 两份 MD | 技能 references |
| --- | --- | --- |
| 日常实例创建时使用 | 取决于启用记忆 | 沿用技能加载机制，独立于三个开关 |
| 自动整理写入 | 启用记忆且文档自动更新 | 技能自动更新 |
| 手动整理写入 | 启用记忆；不看文档自动更新 | 不看技能自动更新 |
| 用户直接编辑/恢复 | 始终允许，仍校验容量与版本冲突 | 首版不新增这类编辑入口 |

后端计算实际可写对象，前端只展示结果，不能由按钮状态承担权限保证。任务中关闭某项后，后续写入该项被拒绝并返回原因；其他项可继续，已完成修改不回滚。没有自动可写对象时不启动新的自动任务。开关不清文件、不重置处理进度，不把关闭时段排除出日志范围。

提示词配置与开关不同：提示词在启动时固定，后续修改不影响执行中的任务；开关在写入时读取当前值。

### 2.3 自动与手动范围

- 自动：距上次自动整理完成至少 24 小时，并新增至少 20 轮已完成的真实用户与主 Agent 交互。工具调用、子 Agent 来信和后台角色运行不单独计数。
- 首次：初始化启用满 24 小时，且新增满 20 轮后才启动；范围包含全部现存可用历史，不能把已有轮数当作初始化后新增轮数。
- 后续：从上次成功处理位置继续，选取启动时已完成且未处理的交互；不固定“最近 N 天”。启动时尚未完成的长任务日后仍须纳入。
- 手动：用户选择开始、结束时间，按每轮最初用户发言时间筛选；只处理启动时已经完成的轮次。结束默认现在，在启动时解析并固定。
- 手动可重读旧范围，不推进自动处理位置、不重置自动计时。用户直接编辑/恢复保存则沿用草稿：重新累计 24 小时与 20 轮，但不跳过未处理日志。
- 一批自动整理正常结束，即统一推进进度。被开关拒绝的某类写入不建立单独补做队列；无需修改也属于完成。失败、取消不能误报整批成功。
- 忙碌时不启动第二个、不排队、不替换当前任务；保留输入。空范围不启动模型，开始晚于结束返回明确校验提示。

### 2.4 编辑、恢复与历史版本

用户点击文档“编辑”即取消整个正在运行的整理，不只是屏蔽该文档写入。编辑期间不启动新整理，迟到写入必须拒绝。取消编辑不恢复旧任务，也不重置计时。修改提示词配置不等同于编辑记忆文档，不取消当前任务。

用户保存直接落盘，不经 AI 审核。user 上限 500 字符，memory 上限 1,200 字符；超限显示差额，不保存、不截断。技能 references 每个 Skill 合计 5,000 字符；原已超限者可保留，修改后不得继续增长。

每次实际有变化的用户保存、历史恢复、AI 整批修改，为相关文件保留操作前内容；同一 AI 批次最多新增一个该文件的历史版本。各保留最近八版，显示时间与修改来源。恢复只替换选中的文件，并将替换前当前内容按同样规则保留；不改变开关、不锁定恢复结果。

### 2.5 提示词与临时笔记

自动和手动提示词始终分别保存，不因成功、取消、失败清空，不由 AI 修改。任务快照同时传给整理与审核角色。长期信息可以成为提案依据，整理指令不机械转为记忆；固定工具权限、证据要求和容量规则仍有效。

临时笔记仅属于一次任务：整理角色读写，审核角色可读；保存已读位置、候选与来源、冲突和待核实事项。路径由后端固定。压缩、中断、重启仍可读；完成结果与进度持久化后删除，明确取消也删除，等待恢复的失败保留。清理失败只重试删除，不重做整理。

```text

  → AgentManager
  → ProcessRuntime
  → execution_worker
  → AgentRuntime（创建时组装系统提示词）
  → AgentLoop → 工具
  → 检查点、会话快照、实时日志
```

新增整理链：

```text
自动门槛 / 用户页手动请求
  → 记忆服务取得全局任务名额
  → 固定日志清单、提示词、任务 ID
  → 整理角色：分段读取 / 临时笔记 / 提交提案
  → 审核角色：核对原始依据 / 调用受限写入
  → 后端逐次检查当前开关、取消状态、路径、容量、版本
  → 保存结果和共用进度
  → 清理本批临时资料
```

## 4. 模块边界与数据归属

建议在 `agent/core/memory/` 内集中本功能，按真实职责拆分，不建立通用工作流框架：

| 模块（建议名） | 负责 | 不负责 |
| --- | --- | --- |
| `service.py` | 任务启动、取消、编辑互斥、阶段推进、完成收口 | 页面布局、模型循环实现 |
| `store.py` | 配置、文档、版本、任务记录、操作编号、共用进度、原子保存 | 模型判断、扫描所有会话 |
| `sources.py` | 日志识别、增量解码适配、轮次范围、分页、来源位置 | 写正式记忆、定义 UI 状态 |
| `tools.py` | 受限读取、笔记、提案、写入入口与校验 | 任意路径文件操作、终端能力 |
| `roles.py` | 两个后台角色的固定提示词、工具白名单、执行配置 | 另造 Agent Loop 或多 Agent 协作总线 |

调度先作为服务的小型定时检查，不为两个开关分别建 scheduler。FastAPI 路由、CLI 和前端只调用服务，不重复实现业务。根据实际文件体量可合并小模块，不为空壳抽象新增类。

建议数据布局：

```text
data_root/
  user.md
  memory.md
  memory-state/
    config.json                 三个开关、两份提示词、结构版本
    progress.json               首次基线、共用自动进度、门槛计数
    versions/user/              最近八个修改前版本及元数据
    versions/memory/
    tasks/<id>/                阶段、固定范围、提案、检查点、操作结果
  temp/memory/<task-id>/        临时笔记及必要的本批读取辅助资料
```

以上路径通过 runtime_layout 注入，不能拼当前用户项目目录，不能写 EXE 安装资源目录。任务记录不无限保留完整 history/日志副本；收尾只保留必要的状态和审计摘要，清理可再生中间产物。终态记录保留量和失败重试值在编码前作为集中常量明确，不散落在页面和工具里。

配置缺失时只初始化一次，不覆盖现存 MD；结构携带 schema_version。升级迁移保留开关、两份提示词和用户内容，遇到未知版本明确报错，不静默重置。配置可使用字段 `enabled`、`documents_auto_update`、`skills_auto_update`、`auto_prompt`、`manual_prompt`，后端响应同时返回计算后的有效写入对象。

## 5. 关键实现链路与边界

### 5.1 创建时加载系统提示词

1. Runtime 创建时从 data_root 读取配置与两份当前 MD。
2. `enabled=false` 则不组装记忆段；开启时使用独立的记忆段，避免混淆为项目 AGENTS.md。
3. 系统提示词和 ContextManager 在同一次初始化拿到相同内容。
4. 当前实例后续 handle、工具返回、压缩和内部循环均不重读文件，不替换 history。
5. 应用重启恢复会话时，沿现有实例创建逻辑读最新记忆；不要从旧检查点恢复已过期的系统提示词覆盖新组装值。

子 Agent 沿用同一创建边界，不增刷新逻辑。后台整理/审核角色应使用专用固定提示词，不能继承普通助手的终端、委派等能力或让待审核记忆改变其职责。

### 5.2 范围、计数与日志读取

不能仅用“最大用户发言时间”当水位：跨会话长任务可能早发言、晚完成。建议以可稳定恢复的轮次身份（session_id + request_id）去重，结合完成顺序/位置与本批清单记录覆盖范围；旧日志的兼容身份由读取适配器产生，不依赖模型判断。

同时核对 `SessionKind`、父子关系和消息来源，不能只凭 role=user 计数；内部 Agent 来信也可能以 user 形式出现在模型历史中。每个真实用户轮次只计算一次，失败重试同一轮不能重复增加门槛。

新旧日志适配要求：

- 复用 v3 引用解码语义，不能对任意字节偏移直接读取而丢失前面的引用字典；不要为每一页重新完整展开整份历史。
- 正文分页按记录/文本片段提供 next_cursor、has_more、来源标识、缺失/截断信息，限制工具输出体积；必要时增量构建本批读取索引。
- 优先读取用户输入、输出、工具调用及结果和运行状态，不把每次 llm_input 中重复的历史当作新证据。
- 超大单条记录也必须能分段继续，而不是截断后永久丢掉后半段。原始已截断的数据只能标明不足。
- 旧日志缺失时仅补充仍保存的 session 信息；缺失轮次时间的旧记录不能冒用会话创建时间通过手动范围筛选。应返回缺口，避免伪造精确时间。
- 时间接口传带时区时间并在后端统一比较；手动边界建议统一为开始包含、结束不包含，UI 与读取器使用同一口径。旧无时区日志按运行机器的约定适配，记录不确定性。

现有日志按文件修改时间清理超过 7 天的文件；“全历史”不等于永久保存的全量证据。本功能不自动延长全局保留时间。活动任务需要与清理协调：任务使用中的日志受有限保护，终态释放；用户明确删除会话优先，不为整理偷偷保留被删除会话的永久副本。恢复发现来源缺失时记录缺口，不能据此确认工具成功。

### 5.3 共用任务和后台角色

建议持久阶段：准备 → 整理 → 审核 → 完成/无需修改，另有失败待恢复、已取消。阶段推进必须写盘；应用退出是中断，不写成用户取消。

准备阶段在锁内取得名额、保存配置快照和范围，随后释放短锁再执行模型调用。不可持写入锁等待模型网络返回。两个角色顺序复用 ProcessRuntime/worker，使用默认模型，不互发消息、不召唤第三个角色；后台运行用 SYSTEM 身份隔离，避免进入普通用户列表或再次成为整理来源。

Web 与 CLI 共用同一 data_root 时，进程内锁不足以保证单任务。需进程间任务所有权/文件锁，避免两端各启动一个 scheduler。通过服务生命周期显式启动与关闭，避免 import 路由时顺带启动第二个调度器。CLI 不必先新增完整管理命令，但其用户对话计数、记忆加载和后台服务必须走相同能力。

角色工具必须在实际执行入口再次白名单校验。现有 `resolve_tools` 主要负责提供给模型的工具集合，编码时必须核查执行分发是否能被伪造工具名绕过；不以隐藏定义当作权限限制。模型不得直接修改配置、处理进度、任务状态或历史备份。

### 5.4 编辑、写入与竞态

拟采用短期编辑凭证，开始编辑时取消活动任务并取得编辑权；页面关闭/断线通过有效期释放，避免永久阻塞。保存、取消使用同一凭证；凭证失效时保留前端草稿、提示重新进入编辑，不能无提示覆盖其他窗口的新内容。

所有正式写入在同一短写锁内重新检查任务有效性、实时开关和文件版本，再执行版本备份与原子替换。使用稳定操作编号保存结果，重启遇到“已写文件但回执丢失”时先核对已执行结果，不能重复追加。记录每批每文件的初始版本标识，防止部分失败重试耗尽八版额度。

跨文件不做全批回滚；已保存修改保留，失败从未完成步骤继续。后台更新和用户编辑取消的顺序必须由锁及任务标记保证，不通过延时等待猜测。配置修改和写入权限检查也需共享明确的提交顺序：开关关闭接口返回成功后，不应再有使用旧权限的新写入提交。

字符计数实施口径建议：统一 LF 换行，按 Unicode 码点计数，空白与换行计入；Python 用一致的文本长度，前端不要直接用 UTF-16 的 string.length 计算 emoji。禁止静默 trim 用户文档。恢复历史版本也执行相同容量校验。

### 5.5 技能路径与 EXE 兼容

现有 Runtime 同时读取 `APP_ROOT/skills` 和 `data_root/home/.agents/skills`，打包时两者可能分离。不能把内置资源目录等同于可写数据目录，更不能为了经验更新复制一整套技能加载体系。

后端以 SkillLoader 已解析的技能身份映射真实目录，允许目标限定在批准的运行数据技能 references 中；最终路径解析后检查父目录、符号链接/junction、大小写、绝对路径和 `..`。拒绝 SKILL.md、用户项目技能、其他目录。

实施阶段先验证打包实际布局。若内置技能位于只读安装资源，首版不直接修改安装目录；返回不可写原因，并明确实际可维护技能范围。若要使这些内置技能也可进化，需要沿现有加载机制设计 data_root 中的经验覆盖层并另行确认范围，不能临时放宽沙箱或强写安装目录。此为编码前必须解决的兼容性检查，不宣称当前已具备全技能可写能力。

## 6. FastAPI 接口方案

接口集中到 `/api/memory`，由 `server/routes/memory.py` 转交服务。REST 资源建议如下；名称可按现有路由风格调整，语义不能重复实现。

| 方法与资源 | 输入/结果 | 关键检查 |
| --- | --- | --- |
| GET /config，PATCH /config | 三开关、两提示词、配置版本、有效对象 | PATCH 只改提交字段；空字符串明确表示清空提示词；不改当前任务提示词快照 |
| GET /documents/{target} | user 或 memory 内容、长度、上限、版本 | 固定枚举，不接收文件路径 |
| POST /edits | 目标；返回编辑凭证与基准版本 | 取消当前整理，取得编辑权 |
| PUT /documents/{target} | 凭证、基准版本、完整内容 | 容量、版本、凭证；原子保存，生成一次历史 |
| DELETE /edits/{id} | 取消编辑 | 不复活已取消任务，不重置计时 |
| GET /documents/{target}/versions | 八版元数据 | 不把长正文全部塞进列表 |
| GET /documents/{target}/versions/{id} | 指定版本正文 | 限目标，防任意路径读取 |
| POST /documents/{target}/restorations | version_id、编辑凭证、基准版本 | 与手动保存共用服务链路 |
| POST /tasks | 手动时间范围 | 服务加载已保存提示词；忙碌/编辑中拒绝，空范围不调用模型 |
| GET /tasks/current，GET /tasks/{id} | 阶段、有效对象、结果、错误、缺口 | 不在轮询中返回完整日志或笔记 |

补充提示词输入采用显式保存；有未保存修改时先保存成功再启动，保证启动使用的是用户看到的版本。服务端启动响应携带采用的配置版本与实际范围，防止多窗口误解。前端暂存输入不依赖请求失败后的重置。

错误区分：参数/超限、资源不存在、忙碌、版本冲突/凭证失效、任务已取消、目标被禁用、底层 IO/模型失败。HTTP 可分别使用 422、404、409 等现有约定，工具返回结构化业务结果；不可一律显示“更新失败”。

## 7. 实施顺序与阶段验收

### 阶段一：确认接入与数据底座

补查执行分发白名单、角色配置跨进程序列化、现有时间和身份记录、EXE 可写 Skill 路径；确认与日志清理、删除会话的协调。建立最小 memory 模块、配置迁移、文件和历史存储、写锁及编辑互斥。

验收：全新初始化不覆盖旧文档；重启保留两提示词；三个开关默认开启；两份文档按同口径限长；八版滚动、恢复和 Windows 临时写入失败不破坏当前文件。

### 阶段二：新实例记忆加载

接入 prompt_docs_loader/system_prompt_builder/AgentRuntime 初始化，隔离普通角色与后台角色；不改 handle 或 AgentLoop 的刷新行为。

验收：实例 A 创建后修改文件、关闭记忆，A 的系统提示词保持不变；新实例 B 使用最新配置；重启恢复读取最新内容；history 中没有记忆注入。Web/CLI、主 Agent/子 Agent 的创建行为一致。

### 阶段三：来源与受限工具

实现范围清单、轮次计数、增量日志分段、来源追踪、历史读取、临时笔记、提案和写入工具；将工具绑定本批任务身份，禁止模型自行指定其他任务。

验收：跨会话晚完成不漏；来源去重；压缩后笔记仍可读；工具越权、迟到写入和超限被拒绝；重复操作编号不重复落盘。

### 阶段四：整理、审核与恢复

接入两个后台角色，先打通手动任务，再接自动门槛；统一所有权、阶段检查点、开关即时写入限制和进度提交。添加可控失败重试与生命周期收尾，避免断网时无限调用模型。

验收：真实工作进程使用替身模型跑通两个角色；首次门槛准确；手动任务不动自动进度；部分拒绝不否决整批；同批笔记成功清理、故障保留；重启不重复写；Web/CLI 同开也只有一个任务。

### 阶段五：统一页面与接口

新增记忆组件、客户端方法、类型与 REST 路由；App.tsx 只负责挂载。补齐短标签、说明、生效提示、历史恢复、两提示词保存、时间范围与忙碌状态。状态轮询仅在需要时开启，卸载后停止，避免持续后台请求。

验收：通过组件状态/纯逻辑测试与 TypeScript 构建检查验证开关、超限、忙碌、保存错误和版本冲突；不使用浏览器测试。Electron 共用同一 API，不另建直接读写磁盘的 renderer 通道。

### 阶段六：回归、文档与交付

使用项目 uv 环境运行相关 pytest；中间文件及 pytest 临时目录放根目录 temp。先针对性用例，再执行现有后端回归和前端构建；不得为验证改用另一套依赖环境。记录失败重试参数、数据路径、恢复和清理方式，不留下隐式约定。

实际功能实施后在开发日志记录变更及真实测试结果；验收只以实际运行过的检查为准。

## 8. 必须覆盖的边界测试

按风险合并参数化用例，避免大量只照抄实现的测试：

1. 三开关组合 × 自动/手动/直接编辑，运行中关闭对象、写锁提交竞态、另一对象可正常写入。
2. 中文、emoji、空白、CRLF，恰好上限与超一字符；references 原已超限的缩减和增长。
3. 手动范围边界、同秒多轮、跨会话晚完成、内部来信、无轮次时间、空范围、初始化旧日志不计新增门槛。
4. 新旧日志混用、v3 引用跨页、超长单条分页、损坏尾行、日志已清理/被删除；不把缺失结果认作成功。
5. 用户编辑时审核迟到写入，保存/取消/断线/双窗口冲突；恢复不关开关、不锁定内容。
6. 同批多次修改只保留一版；无变化无新版本；第九版淘汰；恢复后还可查看恢复前内容。
7. 整理与审核使用同一提示词快照，运行中改配置不影响本批；成功/取消/失败均不清空两提示词。
8. 进程在提案提交前、提交后、写入后回执前、进度提交后清理前退出；操作幂等、笔记生命周期、取消不恢复。
9. 实例 A/B 系统提示词生效边界、压缩与重启恢复、主子 Agent 排除计数；不增加刷新、不污染 history。
10. CLI/Web 并存任务互斥、只读 APP_ROOT、中文 data_root、路径穿越/junction/伪造工具名和伪造任务 ID。

## 9. 维护与兼容约束

- 业务规则以 memory 服务为唯一实现，前端、路由、工具只能复用，不能各写一套限长、开关或范围规则。
- 不复制 AgentRuntime、Loop、压缩器、进程监督器或 v3 日志格式；必要扩展必须保持默认角色行为不变。
- 新数据有结构版本，旧会话和日志能降级读取；读不到的证据明确标注，不能静默伪造默认值。
- 文件路径通过 data_root 和 Skill 身份解析；源码运行与 EXE 分离资源布局都能验证。
- 全局协调包含多进程，不仅进程内线程；锁持有时间短，模型调用不持文件写锁。
- 状态完成、进度提交、版本保留与临时清理有明确顺序；日志保留与任务读取互相协调，不留下永久保护文件。
- 对未确认的内置技能覆盖层、重试参数等问题先做局部技术验证并记下最终选择，不以临时硬编码或关闭安全检查赶进度。
- 后续扩展角色不依赖前端入口，也不把记忆整理硬编码为普通子 Agent 对话；保持单 Agent、平等协作和领导/下属模式可继续复用同一 Harness。

完成标准：以上产品动作能沿单一服务链路完成，关键边界有可重复验证，数据可恢复、可迁移，且不引入运行中提示词刷新或独立技能整理系统。
