# 2026-07-14 排队消息撤回与排序

## 背景/原因

AI 运行期间，Web 端已经允许用户继续发送消息并在当前回答结束后顺序执行，但排队消息原先混在聊天流中，只能被动等待，无法撤回或调整执行顺序。用户停止当前回答后，旧逻辑还会立即启动下一条排队消息，也不符合“停止后先保持安静”的预期。

本次迭代只改造前端交互队列，不建设消息总线，不修改后端中断接口、Agent Harness 或 Agent Loop。

## 具体设计

- 排队区参考 Codex 的紧凑布局，移动到输入框正上方，与输入框形成统一的 composer 区域；不再把排队内容渲染成聊天消息卡片。
- 每条消息显示拖拽手柄、当前顺序、单行内容摘要和撤回按钮。队列最多直接展示约三行，更多内容在浅色面板内滚动。
- 排队消息使用前端稳定 ID，允许内容相同的多条消息被分别撤回和排序。
- 用户可拖动手柄改变执行顺序；当前回答结束后，始终按照最新顺序取出队首消息自动执行。
- 点击撤回会打开二次确认框；确认后只删除仍在排队的目标消息，不影响当前回答和其他消息。如果确认期间目标已经开始执行，则提示无法撤回。
- 点击停止时，当前回答进入停止状态，已有队列暂停，不自动启动下一条。队列提示条提供“继续执行”，点击后从当前队首恢复并连续处理。
- 队列暂停期间，用户从输入框发送的新消息优先执行，并视为恢复队列；新消息完成后自动回到旧队列。若回答仍处于停止过程中，多条新消息按发送顺序排列在旧队列之前。
- 优先消息执行期间再次发送的消息按普通规则追加到队尾；撤回最后一条消息后隐藏队列区并清除暂停状态。
- 队列仍保存在前端内存中，刷新页面或重启应用后的恢复不属于本次范围。

## 验收标准

- 正常完成、停止暂停、手动继续和新消息优先恢复四条链路的执行顺序符合设计。
- 重复内容可以精确撤回，拖拽首尾或中间项不会丢消息。
- 消息开始执行后从队列区移除，不再允许撤回或排序。
- 长队列不会撑高聊天区或输入框，队列面板可以独立滚动。
- 前端单元测试和生产构建通过，不增加后端接口。
